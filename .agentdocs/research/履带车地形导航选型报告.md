## 结论先定下来

你现在最接近"可长期实车运行"的，不是再换一个更复杂的 SLAM，而是把已有的 **FAST-LIO + CMU/FAR** 主线补成真正的履带车地形风险系统。

附件里已经具备：

> Mid360 → FAST_LIO → FAST_LIO_LOCALIZATION → 双层 terrain_analysis → FAR → local_planner/pathFollower

这个骨架与我筛选后的第一推荐高度一致；其中 `FAST_LIO_SUPER` 更适合作为研究支线，生产主线继续用原版 FAST-LIO/FAST-LIO2。

我的最终排序是：

1. **首选：Mid360 + FAST-LIO2 + 增强型 CMU 地形分析 + FAR/田垄拓扑 + FALCO**

   * 电脑：NUC
   * 优点：低算力、低延迟、确定性强、已有实车基础、改动最少
   * 关键工作：增强地形代价，而不是重写 SLAM

2. **第二选择：Mid360 + FAST-LIO2 + 2.5D 地形图 + State Lattice/FAR + 地形约束 MPPI**

   * 电脑：较强 NUC 或 Orin NX
   * 优点：局部控制更平滑、对动态障碍和复杂曲线更灵敏
   * 代价：参数和代价函数明显比 FALCO 难调

3. **长期商业软件平台：Mid360 + FAST-LIO2 + 地形版 Nav2 + Smac State Lattice + MPPI + 独立安全监督**

   * 电脑：NUC 或 Orin NX
   * 这里说的是"地形版 Nav2"，绝不是 Cartographer + 默认二维 costmap + Nav2

4. **高端感知版：Mid360 + 1080 全局快门 + elevation_mapping_cupy + 语义可通行性 + MPPI/NMPC**

   * 电脑：Orin NX Super
   * 地形理解能力最高，但工程复杂度和调参风险也最高

## 一、传感器与算力选择

### 1. 传感器排序

| 组合                       |  适用程度 | 建议                                  |
| ------------------------ | ----: | ----------------------------------- |
| **Mid360 单雷达**           | ★★★★★ | 首选基础配置                              |
| **Mid360 + 1080 全局快门海康** | ★★★★★ | Orin 方案首选；相机用于植被、水面、田垄边界和无数据区域辅助判断  |
| **Mid360 + HAP**         | ★★★☆☆ | 仅在速度较高、需要远距离前视时有意义                  |
| **HAP 单雷达**              | ★★☆☆☆ | 不适合作为复杂田垄唯一主雷达                      |
| **雷神 CX12S3 单雷达**        | ★☆☆☆☆ | 若你所说的 C12 是这个型号，不适合作为复杂地形主雷达        |
| **Mid360 + 640 卷帘相机**    | ★★☆☆☆ | 仅作低优先级语义辅助                          |
| **D351i**                |  暂不评分 | 未能核实准确型号；若实际是 D435i，应只作为近距 RGB-D 辅助 |

#### Mid360

Mid360 有 360° 水平视场、约 59° 垂直视场、0.1 m 近距盲区、200k 点/秒、内置 IMU，重量仅 265 g；对于低速履带车，近场环视和垂直覆盖比 HAP 的远距离密度更重要。([Livox][1])

需要注意：

* 水面、黑色低反射物、细线、薄小物体以及部分哑光表面，尤其在 0.1～1 m 内，官方明确表示探测效果不能保证。
* 因此沟渠、水坑和黑色软管不能只靠"看见障碍物"，还必须把**持续无地面数据**视为危险。([Livox][1])

#### HAP

HAP 是 120° × 25° 前向视场、452k 点/秒、10% 反射率下约 150 m 的长距离雷达。它适合汽车式前向感知，但履带车的侧面、后方和近距地面信息不足，因此不适合作为唯一雷达。([Livox][2])

建议只在以下情况下增加 HAP：

* 运行速度明显提高；
* 需要提前看见几十米外人员、车辆或大障碍；
* 需要正前方高密度点云；
* 可以接受第二雷达带来的算力、标定和遮挡问题。

#### 雷神 C12

镭神现有产品资料里比较接近的是 **CX12S3**。该型号是 120° 水平视场，但垂直视场仅 2.2°、约 9 万点/秒，更接近远距离前向扫描器，不足以单独表达车前台阶、沟槽、坡面和两侧地形。([Leishen Intelligent System][3])

所以：

* 若确实是 CX12S3：只能作前向补盲，不能替代 Mid360。
* 若"C12"是另一个型号，应先按完整型号重新判断。

#### 两台海康相机

| 相机            | 建议用途                                  |
| ------------- | ------------------------------------- |
| **1080 全局快门** | 语义分割、田垄边界、植被、水面、远处障碍；也可以用于 FAST-LIVO2 |
| 640 卷帘快门      | 低速辅助观察或一般目标识别，不作为视觉里程计主相机             |

履带底盘振动、急转和起伏会放大卷帘畸变，所以全局快门明显更合适。

### 2. 电脑选择

| 方案                     | NUC 无 GPU | Orin NX Super |
| ---------------------- | --------: | ------------: |
| FAST-LIO2              |        推荐 |            可用 |
| CMU terrain_analysis   |        推荐 |            可用 |
| FAR/FALCO              |        推荐 |            可用 |
| Nav2 Smac + MPPI       |        推荐 |            推荐 |
| FAST-LIVO2             | 可运行但需评估余量 |           可运行 |
| elevation_mapping_cupy |       不适合 |        **推荐** |
| nvblox                 |       不适合 |        **推荐** |
| 视觉语义网络                 |        受限 |        **推荐** |
| 学习型可通行性                |       不适合 |        **推荐** |

Orin NX 可提供最高约 157 TOPS，功耗模式约 10～40 W；JetPack 的 Super 模式主要增加 GPU、DLA 和相关引擎性能。([NVIDIA][4])

但要特别区分：

* FAST-LIO、FAR、CMU local_planner 主要吃 CPU；
* Nav2 官方 MPPI 当前是基于 Eigen 的 CPU 实现；
* Orin 的 GPU 不会自动加速这些模块；
* 只有使用 `elevation_mapping_cupy`、`nvblox`、语义分割或学习模型时，Orin 才真正体现优势。Nav2 MPPI 官方给出的参考结果是在普通 Intel CPU 上可达 100 Hz 以上，但完整地形系统没必要追求这么高，20～50 Hz 更合理。([Nav2 Documentation][5])

因此：

* **纯几何、低延迟、稳定优先：NUC。**
* **视觉语义、GPU 高程图、学习感知：Orin NX Super。**

## 三、方案 A：增强型 CMU/FAR/FALCO——推荐生产方案

### 完整组合

```text
Mid360
→ FAST-LIO2
→ 预建图重定位或局部连续里程计
→ 局部高频地形图 + 扩展低频地形图
→ 田垄拓扑/FAR 全局规划
→ FALCO/CMU motion primitives 局部规划
→ 独立速度与安全监督
→ 履带底盘
```

### 算力

**NUC，无 GPU。**

FAST-LIO2 官方强调计算效率，支持原始点直接匹配、固态雷达和 ARM 平台；这类定位前端不需要为了田垄导航而换成更重的视觉方案。([GitHub][6])

CMU `ground_based_autonomy_basic` 明确面向处理能力有限的车载计算机，除仿真器外的模块均按轻量化和实时运行设计。([GitHub][7])

### 地形图必须包含的量

当前 `terrain_analysis` 的"点云高度或强度代价"还不够。建议固定输出下列十类代价：

1. 地面高度及高度方差；
2. 纵向坡度；
3. 横向坡度；
4. 粗糙度；
5. 最大正台阶；
6. 最大负台阶、沟槽和无数据区；
7. **整个左右履带足迹内的地面支撑比例**；
8. 左右履带高度差、预计横滚和侧翻余量；
9. 底盘离地间隙与托底风险；
10. 地图置信度、观测时间和动态衰减。

对履带车来说，优先级大致是：

> 无数据/沟槽 ＞ 足迹支撑 ＞ 横坡/侧翻 ＞ 台阶 ＞ 粗糙度 ＞ 普通障碍物距离。

不能仅用"中心点所在栅格能否通过"。必须用**完整车体和两条履带的足迹**计算。

### 两层地图建议

| 地图    |         推荐范围 |    推荐频率 | 用途              |
| ----- | -----------: | ------: | --------------- |
| 局部地形图 | 车体周围约 8～12 m | 8～15 Hz | 局部规划、沟槽、台阶、侧翻判断 |
| 扩展地形图 |    约 30～50 m |  2～5 Hz | FAR、绕障和垄头路线选择   |

现有快衰减与慢衰减双实例方向是正确的，不必推翻。

### 全局规划

建议同时保留两种规划模式：

#### 田垄内作业

```text
田垄/行间拓扑图
→ 规定可进入的行
→ 中心线或偏置线
→ 垄头允许转弯区域
```

这样不会因为几何上"更短"而横穿作物、田埂或排水沟。

#### 非结构化区域和垄头绕障

```text
FAR 可视图
→ 边权加入地形风险
→ 输出可尝试路线
```

FAR 的官方实现使用两个 CPU 线程，在其 i7 测试平台上，图更新约占一个线程的 20%，路径搜索低于 3 ms；它能处理已知、未知和动态障碍环境，并曾用于 CMU-OSU 的 DARPA SubT 系统。([GitHub][8])

不过 FAR 原始优势是**几何可达性和快速重规划**，不天然知道履带车会不会侧翻。因此其边代价至少应加入：

* 最大横坡；
* 最大台阶；
* 最小支撑比例；
* 未知区域比例；
* 路径平均粗糙度；
* 预计打滑程度。

### 局部规划

继续使用 CMU `local_planner`/FALCO motion primitives。

它的特点：

* 预生成运动基元；
* 差速运动模型，与履带式 skid-steer 底盘的基本运动形式接近；
* 计算量小；
* 输出行为确定；
* 不会像随机采样控制器那样因参数变化产生较大行为差异。CMU 官方资料也说明其使用运动基元和差速模型。([GitHub][7])

需要额外增加：

* 横坡时限制速度；
* 原地旋转时降低角速度；
* 高粗糙度地面降低加速度；
* 检测到左右履带支撑不均时禁止转向；
* 指令速度与 FAST-LIO 实际速度长期不一致时，判定打滑或陷车。

### 安全层

必须独立于 FAR 和 local_planner：

```text
近场硬障碍停车
沟槽/无地面停车
横滚或俯仰超限停车
定位质量下降减速/停车
持续打滑停车或有限后退
通信或规划超时停车
```

CMU 官方对负障碍也给出了同样方向：最好把传感器装高并向下观察；没有地面数据的区域可以直接作为不可通行区。([GitHub][7])

## 四、方案 B：CMU 地形图 + MPPI

### 完整组合

```text
Mid360
→ FAST-LIO2
→ 增强型双层地形图
→ FAR 或 State Lattice 全局路径
→ MPPI
→ 独立安全监督
```

### 适用场景

* 需要非常平滑的速度变化；
* 障碍物动态性高；
* 垄头转弯空间窄；
* 希望局部控制同时权衡路径、障碍、坡度和车体姿态；
* FALCO 运动基元表现过于离散或保守。

### MPPI 必须增加的 critic

默认二维 MPPI 不认识复杂地形。至少要有：

```text
路径跟踪代价
障碍距离代价
纵坡代价
横坡/横滚代价
正台阶代价
负台阶/未知空间代价
足迹支撑率代价
托底代价
履带打滑代价
加速度和角加速度代价
原地旋转地形风险
```

形式上可以理解为：

```text
总代价 =
  路径误差
+ 障碍风险
+ 坡度风险
+ 侧翻风险
+ 台阶风险
+ 支撑不足风险
+ 未知空间风险
+ 打滑风险
+ 控制变化风险
```

### 评价

| 项目    | 评价                          |
| ----- | --------------------------- |
| 实时性   | 好，目标 20～50 Hz               |
| 地形能力  | 取决于自定义 critic，而不是 MPPI 名称本身 |
| 算力    | 较强 NUC 足够；GPU 不是必须          |
| 调参难度  | 高于 FALCO                    |
| 行为确定性 | 低于固定运动基元                    |
| 商业推荐度 | 第二选择                        |

Nav2 的 MPPI 是采样型预测控制器，支持差速、全向和阿克曼模型，目标函数可插件化，因此适合加入履带车专用地形 critic。([Nav2 Documentation][5])

## 五、方案 C：真正的地形版 Nav2

这不是已被否掉的"Cartographer + Nav2"。

### 完整组合

```text
Mid360
→ FAST-LIO2 / 地图重定位
→ 3D 地面分割
→ Ground Consistency
→ 自定义 2.5D 履带车地形层
→ Smac State Lattice
→ MPPI
→ Collision Monitor
```

### 必要组成

#### Ground Consistency

Nav2 当前的 Ground Consistency Layer 针对 3D LiDAR 和非平面户外环境，通过地面分割、证据累积和相对高度判断区分地面与障碍；官方教程目前要求 ROS 2 Jazzy。([Nav2 Documentation][9])

它可以解决：

* 地面倾斜时被默认 costmap 误认为障碍；
* 单帧噪点；
* 非平面地面；
* 地面与高出地面的障碍区分。

但它仍然不能完整解决：

* 左右履带支撑率；
* 横滚和侧翻风险；
* 底盘托底；
* 松软泥地和打滑；
* 负台阶深度。

所以 Ground Consistency 只能作为前处理，后面仍需自定义地形层。

#### Smac State Lattice

比普通二维 A* 更适合：

* 有车体方向约束；
* 有完整矩形/履带足迹；
* 不能随意横向移动；
* 需要有限曲率和可执行路径。

#### MPPI

负责高频局部控制，但使用上面的自定义地形代价。

#### Collision Monitor

Nav2 Collision Monitor 绕过 costmap 和轨迹规划器，直接根据传感器数据执行减速或紧急停车，适合作为软件安全层；官方也明确说明它不是安全认证硬件的替代品。([Nav2 Documentation][10])

### 评价

| 项目     | 评价               |
| ------ | ---------------- |
| 商业软件维护 | 最好               |
| 插件化    | 最好               |
| 户外默认能力 | 仍然不够，必须增加地形层     |
| 初始开发量  | 高于现有 ROS1 CMU 方案 |
| 长期扩展性  | 很好               |
| 推荐定位   | 产品平台方案           |

Nav2 由专门团队持续维护并提供商业支持服务，比大量无人维护的论文仓库更适合作为长期软件平台。([GitHub][11])

## 六、方案 D：Orin 高端地形感知

### 完整组合

```text
Mid360 + 1080 全局快门
→ FAST-LIO2 或 FAST-LIVO2
→ elevation_mapping_cupy
→ 几何可通行性 + 视觉语义
→ State Lattice / PUTN / FAR
→ 地形 MPPI 或 NMPC
```

### elevation_mapping_cupy 的能力

该项目使用 GPU 构建高程图，并包含：

* 高度漂移补偿；
* 可见性清理和射线清除；
* 悬空障碍处理；
* 学习型可通行性滤波；
* 平面分割；
* 几何、RGB 和语义多模态融合；
* MIT 许可证。([GitHub][12])

### 相机承担的任务

建议只让相机负责雷达不擅长的类别：

* 水面；
* 密集高草与低矮植被；
* 作物和可行驶地面区分；
* 田垄边界；
* 塑料膜、软管和细线；
* 松软泥地的外观提示；
* 人和动物。

几何安全判断仍以 LiDAR 地形为主。

### FAST-LIVO2 是否值得

FAST-LIVO2 是高效的激光—惯性—视觉紧耦合里程计，适合激光几何退化或需要彩色地图的环境。([GitHub][13])

但不建议默认替换 FAST-LIO2：

* 相机增加了标定、曝光、污染、逆光和季节变化风险；
* 小田垄中的重复作物纹理不一定持续提供稳定约束；
* 相机更适合先做独立语义感知；
* 只有实测 FAST-LIO2 在长直重复田垄中明显退化，再考虑 FAST-LIVO2。

## 七、其他候选方案

### 1. PUTN

```text
点云局部平面拟合
→ PF-RRT* 全局规划
→ GPR 地形建模
→ NMPC 局部控制
```

PUTN 专门针对户外不平整地形，核心包含 PF-RRT*、高斯过程回归和 NMPC，并有粗糙地形实车实验。([GitHub][14])

评价：

* 地形建模思路有价值；
* 纵坡、平整度和局部平面处理比二维导航合理；
* 采样规划和 NMPC 调参成本较高；
* 代码和生态更偏论文验证；
* 适合作为地形规划对照，不建议直接作为第一商用主线。

### 2. Mesh Navigation

MeshNav 在三角网格表面上规划，支持高度差、粗糙度、坡度、山脊、净空、边界和障碍等地图层，并提供 Dijkstra、连续向量场规划和 MeshMPPI。([GitHub][15])

优点：

* 真正保留三维地表；
* 适合明显多层、斜坡、堤坝、地下空间或已知复杂表面；
* BSD-3-Clause 许可证。([GitHub][15])

缺点：

* 对实时变化的泥地、植被和作物环境不如局部高程图自然；
* 在线网格维护复杂；
* 对普通小田垄偏重。

适合：

* 预建静态场地；
* 大型堤坝、坡地、矿区或隧道；
* 不适合作为普通农田第一方案。

### 3. nvblox + Nav2

NVIDIA nvblox 可从深度相机或 3D LiDAR 在 GPU 上实时重建三维环境，然后输出二维 costmap 给 Nav2。([GitHub][16])

优点：

* 稠密障碍重建；
* 动态障碍清除；
* GPU 实时性好；
* 与 Orin 和 Nav2 集成成熟。

问题：

* 最终供普通 Nav2 使用的仍是二维切片；
* "有障碍/没障碍"不等于"履带车稳定可通过"；
* 不直接表达横坡、侧翻、足迹支撑和打滑。

结论：

> 可作为障碍地图模块，不能单独作为田垄地形系统。

### 4. Point-LIO

Point-LIO 的优势是点级更新、高带宽里程计输出，官方项目报告可达到 4～8 kHz，并强调严重振动和激烈运动条件。([GitHub][17])

适合：

* 车体振动极强；
* 控制器确实需要极高频状态；
* FAST-LIO2 实测存在明显时延；
* RoboMaster 或高速无人车式快速运动。

不建议默认替换 FAST-LIO2，因为：

* 田垄车通常不是激烈运动平台；
* 里程计频率高不代表地形判断正确；
* 真正限制反应速度的往往是地形图和控制器，而不是 LIO 输出频率。

### 5. MoveBase3D

MoveBase3D 包含平面拟合、3D Grid Map、PF-RRT*、GPR 和 DWA；其仓库推荐 11 代 NUC i7 或以上，并明确写有"仅供科研测试使用，请勿商用"。([GitHub][18])

结论：

* 可以阅读其平面拟合和参数组织；
* 可以作为 PUTN 的易读参考；
* 不建议作为生产主线；
* 不应因为名称含"3D"就认为它比 CMU/FAR 更成熟；
* DWA 局部层对履带侧滑和侧翻约束仍然不足。

### 6. 学习型可通行性

可使用视觉或 LiDAR 网络判断：

* 草、泥、水、沙、作物；
* 软硬地面；
* 车辆历史通过经验；
* 几何上相似、实际摩擦不同的区域。

建议形式：

```text
几何安全硬约束
+ 学习模型提供软代价
```

禁止形式：

```text
端到端视觉网络
→ 直接输出速度
```

在商业设备上，学习结果只能改变路径偏好，不能越过：

* 最大坡度；
* 最大横坡；
* 最大台阶；
* 最小支撑率；
* 沟槽；
* 近场硬障碍；
* 定位失效停车。

## 八、RoboMaster 方案究竟值得借鉴什么

目前公开的 RoboMaster 哨兵方案中，确实存在：

* Mid360；
* FAST-LIO2 或 Point-LIO；
* NDT/ICP 重定位；
* Nav2；
* MPPI；
* NUC。

例如 2025 年公开方案采用 Mid360、FAST-LIO-v2、Nav2 和 MPPI；另一个团队明确表示从 Jetson NX 转向 NUC，使用 Mid360 + Point-LIO，以利用 CPU 多线程。([GitHub][19])

值得借鉴的是：

1. 高频 LIO 或状态预测；
2. 高频局部控制；
3. 较短预测时域；
4. 局部地图尺寸小；
5. 全局规划与局部避障异步；
6. 紧急停车链路独立；
7. NUC 多线程调度。

不能直接照搬的是：

1. 二维或简单 2.5D costmap；
2. 默认 MPPI critic；
3. 对地面支撑和横坡不建模；
4. 把竞技场坡道等同于泥地、沟槽、田埂和植被；
5. 将高频控制等同于正确的越野决策。

核心结论是：

> RoboMaster 的"灵敏"主要来自高频状态估计和高频控制，不是因为它已经解决了复杂野外地形理解。

一个 3 ms 的规划器，在错误的二维地图上仍会高速做出错误决定。

## 十一、建议的实时频率目标

以下是系统目标，不是要求所有模块同频运行。

| 模块                |       建议频率 |
| ----------------- | ---------: |
| IMU 状态预测/控制侧状态    | 100～200 Hz |
| 独立近场安全监控          |  50～100 Hz |
| 局部控制/FALCO 或 MPPI |   20～50 Hz |
| 局部地形图             |    8～15 Hz |
| 语义感知              |    5～15 Hz |
| FAR/全局重规划         |     1～5 Hz |
| 扩展地形图             |     2～5 Hz |
| 全局任务/田垄拓扑规划       |      按任务触发 |

灵敏性的关键是：

```text
安全与控制高频
地形中频
全局规划低频
```

不是让所有点云、SLAM、全局规划和视觉网络都运行在相同频率。

## 十二、商业采购或技术服务型方案

### 1. Nature Robots

与应用领域最接近。其官方方案面向农业机器，包含混合定位、果园/葡萄园行间跟随，并明确展示了不平整葡萄园、GNSS 受限果园和蔬菜园应用。([Nature Robots][20])

评价：

* 领域匹配度最高；
* 适合直接采购模块或合作开发；
* 更偏农业结构化行间和作业流程；
* 需要确认是否支持自有履带平台、传感器和中国地区服务。

### 2. Tare Robotics

Tare 的公开平台本身使用 Mid360 和 i7，软件包含 LiDAR SLAM、碰撞避免、可通行性分析、路线规划和自主探索；官方也明确欢迎将其开源栈迁移到定制平台用于商业产品开发。([Tare Robotics][21])

评价：

* 与现有 CMU/FAR 技术路线最相近；
* 非农业专用；
* 很适合做技术参考、原型验证或购买支持。

### 3. Clearpath OutdoorNav

OutdoorNav 是面向 OEM、开发者和研究机构的户外车辆自主导航软件，支持 Clearpath 与第三方平台，但基本定位是 GPS/融合定位驱动的户外自主系统。([Clearpath Robotics][22])

评价：

* 商业支持体系强；
* 适合增加 RTK/GNSS 的大范围户外车辆；
* 对小田垄内部细致地形的处理仍需确认；
* 在当前"无 GNSS 设备清单"的前提下不是第一选择。

采购型排序：

> **Nature Robots ＞ Tare Robotics ＞ Clearpath OutdoorNav**

分别对应：

> 农业匹配度 ＞ 当前技术路线相似度 ＞ OEM 户外平台成熟度。

## 最终推荐配置

### 生产首选：低算力、最快落地

```text
传感器：
  Mid360
  1080 全局快门相机仅作可选语义辅助

计算机：
  NUC

定位：
  原版 FAST-LIO2
  + 现有地图重定位

地形：
  双层 terrain_analysis
  + 坡度
  + 横坡
  + 粗糙度
  + 正/负台阶
  + 无数据
  + 完整履带足迹支撑率
  + 横滚/托底风险
  + 地图置信度

全局：
  田垄拓扑/中心线
  + FAR 负责垄头、未知区域和绕障
  + FAR 边权加入地形风险

局部：
  CMU FALCO/local_planner
  + 姿态限速
  + 打滑检测
  + 地形相关速度上限

安全：
  独立近场停车
  + 沟槽停车
  + 姿态超限停车
  + 定位失效停车
```

### Orin 高性能配置

```text
Mid360 + 1080 全局快门
→ FAST-LIO2
→ elevation_mapping_cupy
→ 几何地形 + 视觉语义
→ State Lattice/FAR
→ 地形 MPPI
→ 独立安全监督
```

### 最重要的判断

**第一生产方案应当继续建立在当前 CMU/FAR 主线上。**

真正值得投入的部分依次是：

1. 完整履带足迹地形判断；
2. 负障碍与无数据处理；
3. 横坡、侧翻和托底约束；
4. 打滑检测与地形限速；
5. 田垄拓扑与 FAR 的组合；
6. 独立安全监督；
7. 最后才是 FAST-LIVO2、GPU 高程图或学习模型。

这条路线比换成 MoveBase3D、默认 Nav2、双雷达或更复杂 SLAM，更有可能快速得到稳定的野外实车结果。
