## 1. CMU noetic 接口基线

- 归档日期：2026-04-12
- 目的：把 `ground_based_autonomy_basic/noetic` 中与当前项目最相关的运行时接口直接摘出来，避免继续把“官方基线未知”当成未决项。

---

### 1. 结论先行

#### 1.1 已确认事实
如果我们直接对接 `ground_based_autonomy_basic/noetic`，则官方公开接口基线为：

| 语义 | Topic | 类型 |
|---|---|---|
| 状态估计 | `/state_estimation` | `nav_msgs/Odometry` |
| 注册点云 | `/registered_scan` | `sensor_msgs/PointCloud2` |
| rolling waypoint | `/way_point` | `geometry_msgs/PointStamped` |
| speed | `/speed` | `std_msgs/Float32` |
| navigation boundary | `/navigation_boundary` | `geometry_msgs/PolygonStamped` |
| terrain map | `/terrain_map` | `sensor_msgs/PointCloud2` |
| terrain map clearing | `/map_clearing` | `std_msgs/Float32` |

#### 1.2 直接工程含义
- stock CMU local southbound 是 **点式接口**，不是 `nav_msgs/Path` 接口。
- 如果我们北向从 FAR 拿到的是 route/path，那么 Adapter 必须负责 **Path -> rolling Point** 的折叠。
- terrain_analysis 的 launch 入口不是未知项，项目未决的是“怎么接进我们自己的 launch 编排”。

### 2. 证据摘录

#### 2.1 README 中的系统定位与基础接口
`README.md` 明确写到：
- 仓库位于 state estimation 之上、high-level planning 之下
- real robot 场景下，状态估计通过 `/state_estimation` 发布 `nav_msgs::Odometry`
- 注册点云通过 `/registered_scan` 发布 `sensor_msgs::PointCloud2`
- 底盘控制应转发 `/cmd_vel`

同时 README 还明确：

- `/terrain_map` 为 `sensor_msgs::PointCloud2`
- 点类型为 `pcl::PointXYZI`
- `intensity` 字段表示 cost
- `/map_clearing` 用于 terrain map clearing
- `noDataObstacle=true` 可用于 negative obstacle 处理

#### 2.2 waypoint_example 给出的高层到 local 接口
`waypointExample.cpp` 中直接声明：
- 订阅 `/state_estimation`
- 发布 `/way_point`
- 发布 `/speed`
- 发布 `/navigation_boundary`

其类型分别为：
- `/state_estimation` -> `nav_msgs::Odometry`
- `/way_point` -> `geometry_msgs::PointStamped`

- `/navigation_boundary` -> `geometry_msgs::PolygonStamped`

#### 2.3 localPlanner.cpp 中的真实订阅项

- 订阅 `/navigation_boundary`

因此 `/way_point` / `/speed` / `/navigation_boundary` 不是 README 层面的示意，而是代码层面的真实接口。

#### 2.4 terrain_analysis 的 launch 入口
`terrain_analysis.launch` 中直接定义：

`local_planner.launch` 中直接存在：
- `<!--include file="$(find terrain_analysis)/launch/terrain_analysis.launch" /-->`
- `useTerrainAnalysis` 参数

这说明官方 noetic 基线已经给出了 terrain_analysis 的标准接入位，只是默认未启用。

## 2. Global-to-Local Adapter V1 合同

- 归档日期：2026-04-12
- 任务性质：V1 接口合同定义
- 适用对象：`FAST-LIO2 + FAST_LIO_LOCALIZATION + FAR Planner + CMU Local Planner`
- 目标：把 `Route Planner Layer -> Base Autonomy Layer` 的接口从概念描述收敛为可执行的 V1 合同

---

### 1. 合同结论

#### 1.1 事实
基于 `ground_based_autonomy_basic/noetic` 的公开实现，可以确认 stock CMU local 的 southbound 运行时接口为：
- `/way_point` -> `geometry_msgs/PointStamped`
- `/speed` -> `std_msgs/Float32`
- `/navigation_boundary` -> `geometry_msgs/PolygonStamped`
- 可选 `/terrain_map` -> `sensor_msgs/PointCloud2`

同时，其上游状态估计基线为：
- `/state_estimation` -> `nav_msgs/Odometry`
- `/registered_scan` -> `sensor_msgs/PointCloud2`

#### 1.2 推断
因此，当前项目中的 `Global-to-Local Adapter` 不是“锦上添花”的封装层，而是：

> **FAR Planner 的路径语义与 CMU Local Planner 的点式 southbound 合同之间不可省略的接口收敛层。**

#### 1.3 V1 定位
V1 Adapter 必须同时满足两个约束：
1. **北向**能接收 FAR route / ref path、Mission speed mode、可选 boundary
2. **南向**若直连 stock CMU noetic，则必须收敛到：
   - rolling `/way_point`
   - `/speed`
   - `/navigation_boundary`

#### 1.4 非目标
V1 Adapter 不负责：
- 重新规划全局路径
- 代替 CMU local 做局部避障
- 代替 Mission Executor 做任务流转
- 代替 Localization Manager 做定位融合
- 自己维护一套新的局部控制器

---

### 2. 分层位置与上下游边界

#### 2.1 层级位置

```text
Mission Executor
  -> FAR Planner
  -> Global-to-Local Adapter
  -> CMU Local Planner
  -> cmd_vel
```

#### 2.2 上游边界
上游来源分为两类：

##### A. Route Planner Layer（FAR）
负责提供：
- route / ref path
- waypoint 候选
- 可选 navigation boundary

##### B. Mission Layer（Mission Executor）
负责提供：
- 当前目标锚点类型
- 当前速度模式请求
- 拍照前 / 地头转向 / 恢复等运行语义

#### 2.3 下游边界
下游为 Base Autonomy Layer，即 CMU Local Planner。若采用 stock `ground_based_autonomy_basic/noetic`，其 southbound 期望消费的是：
- 单个滚动局部目标点 `/way_point`
- 当前速度 `/speed`
- 可选边界 `/navigation_boundary`

而不是直接消费完整 Mission 语义，也不是直接消费整条 `nav_msgs/Path`。

---

### 3. 设计原则

#### 3.1 薄层原则
Adapter 不应做“第二个 planner”。

V1 只允许：
- 裁剪
- 重采样
- 选择 rolling waypoint
- 转换
- 滚动更新
- 降级处理

不允许：
- 新增独立路径搜索
- 自己做 obstacle avoidance
- 自己决策 route 绕行

#### 3.2 地图坐标一致性原则
V1 约束所有 route / local goal / boundary 都在统一全局 frame 下表达，默认候选为 `map`。

如果状态估计层最终输出不是 `map`，必须先由 Localization Manager 统一，再进入 Adapter。

#### 3.3 Path-In / Point-Out 原则
北向输入可以是 `Path` 或等价 route 结构；但若南向对接 stock CMU noetic，则最终输出必须收敛为：
- **一个当前滚动 waypoint 点**
- **一个速度目标**
- **一个可选边界**

内部可保留 waypoint window 作为计算与调试结构，但不能把它误写成南向原生合同。

#### 3.4 先路径、后边界原则
V1 优先保证：
1. route -> rolling waypoint 稳定滚动
2. speed mode 可切换
3. 直连 stock CMU local 不引入额外修改

`navigation boundaries` 可首期保留接口，但允许延后进入实装。

---

### 4. 北向逻辑输入合同（Logic Contract In）

#### 4.1 必需输入

##### 输入 I1：当前全局位姿
- 来源：State Estimation Layer
- 建议基线：`/state_estimation` -> `nav_msgs/Odometry`
- 用途：
  - 计算 route 上的最近点
  - 计算 rolling waypoint 选择位置
  - 判断 route 滚动更新位置

##### 输入 I2：route / ref path
- 来源：FAR Planner
- 语义：按顺序排列的全局可行路线
- 最小字段要求：
  - frame_id
  - 有序点列
  - 至少包含 x / y / z
  - 最好包含 yaw 或切向方向信息

##### 输入 I3：当前速度模式
- 来源：Mission Executor
- 语义：当前作业上下文对应的速度意图
- V1 建议枚举：
  - `CRUISE`
  - `APPROACH`
  - `TURN`
  - `RECOVERY`
  - `STOP`

#### 4.2 可选输入

##### 输入 O1：navigation boundary
- 来源：FAR Planner 或 Mission Layer
- 语义：局部可通行边界 / 作业边界约束
- V1 状态：**接口保留，允许缺席**

##### 输入 O2：目标锚点类型
- 来源：Mission Executor
- 语义：当前目标属于行点、拍照点、地头点等
- 用途：辅助速度模式切换和 rolling 规则调整

##### 输入 O3：terrain map 可用性标志
- 来源：Base Autonomy / terrain_analysis
- 用途：用于调试与保护逻辑，不作为 V1 必需前置条件

---

### 5. 南向 ROS 合同（Logic Contract Out）

#### 5.1 必需输出

##### 输出 O1：rolling local waypoint
- 面向：stock CMU Local Planner
- Topic：`/way_point`
- 类型：`geometry_msgs/PointStamped`
- 语义：从全局 route 中折叠出的当前局部引导点
- 要求：
  - 与 route 同一 frame
  - 始终位于机器人前方或当前有效推进方向上
  - 能随机器人推进持续滚动更新

##### 输出 O2：local speed target
- 面向：stock CMU Local Planner
- Topic：`/speed`
- 类型：`std_msgs/Float32`
- 语义：当前局部执行速度目标
- 要求：
  - 来自 Mission 的速度模式映射
  - 不直接硬编码在 planner 中
  - 支持运行时切换

#### 5.2 可选输出

##### 输出 O3：local navigation boundary
- 面向：stock CMU Local Planner
- Topic：`/navigation_boundary`
- 类型：`geometry_msgs/PolygonStamped`
- 语义：当前局部约束边界
- V1 状态：可选

##### 输出 O4：adapter status
- 面向：调试 / 监控
- 建议内容：
  - 当前 route 是否可用
  - 当前 rolling waypoint 索引
  - 当前 speed mode
  - boundary 是否启用
  - 最近一次降级原因

##### 输出 O5：debug waypoint window（仅内部）
- 面向：调试 / RViz / 录包
- 推荐类型：`nav_msgs/Path`
- 说明：该输出只用于内部可视化与诊断，不等同于 stock CMU local 的 southbound 原生输入合同。

### 8. Adapter V1 处理流程

#### 8.1 主循环
Adapter 每次收到新位姿或新 route 时，执行：
1. 检查 route 是否可用
2. 检查 frame 是否一致
3. 在 route 上找到当前位置对应的最近索引
4. 从最近索引向前截取内部 waypoint window（仅用于计算）
5. 按 look-ahead / 距离 / 曲率规则选出当前 rolling waypoint
6. 根据速度模式映射输出 `/speed`
7. 若 boundary 可用，则同步输出 `/navigation_boundary`
8. 发布 `/way_point` 与 adapter status

#### 8.2 rolling waypoint 选择规则（V1）
V1 建议采用最简单可执行规则：
- 使用当前位置到 route 的最近点作为参考起点
- 向前取固定弧长或固定点数形成内部 window
- 在 window 内选择满足最小前向距离的一个点作为 `/way_point`
- 若剩余路径不足，则发布终点附近的最后一个有效点
- 若当前位置偏离 route 超过阈值，则触发 route 失效保护逻辑

#### 8.3 为什么要保留内部 window
内部 window 仍然有价值，因为它可用于：
- 调试 FAR route 与 local 执行的一致性
- 平滑 rolling waypoint 的推进节奏
- 记录切换点、索引推进与偏离情况

但它的地位是：
- **内部结构 / 调试结构**
- **不是 southbound 原生消息合同**

---

### 9. 速度模式映射规则（V1）

V1 不直接传“任务语义”，只传速度目标。

建议映射：
- `CRUISE` -> 巡航速度
- `APPROACH` -> 接近拍照点 / 目标点减速
- `TURN` -> 地头转向低速
- `RECOVERY` -> 恢复模式保守速度
- `STOP` -> 0 速度

具体速度值不写死在代码中，应放在参数中：
- `speed_cruise`
- `speed_approach`
- `speed_turn`
- `speed_recovery`

---

### 10. boundary 处理规则（V1）

V1 对 boundary 的策略建议为：
- **首期允许关闭**
- 若 FAR 可稳定给出边界，则 pass-through 到 `/navigation_boundary`
- 暂不在 Adapter 中做复杂 boundary 生成算法

#### 原因
当前主闭环风险更大的是：
- route -> rolling waypoint 是否顺畅
- speed mode 切换是否稳定
- stock CMU southbound 是否能无歧义直连

而不是 boundary 的高级生成。

---

### 11. 失败与降级策略

#### 11.1 route 缺失
- 不发布新的 `/way_point`
- 发布 `STOP` 或进入安全保守状态
- adapter status 标记 `ROUTE_MISSING`

#### 11.2 frame 不一致
- 拒绝发布下游指令
- adapter status 标记 `FRAME_MISMATCH`
- 记录最近一次错误信息

#### 11.3 当前位姿偏离 route 过大
- 当前 rolling waypoint 失效
- 等待 FAR 更新 route 或进入恢复逻辑
- adapter status 标记 `ROUTE_DEVIATED`

#### 11.4 speed mode 缺失
- 使用默认保守模式 `CRUISE` 或 `APPROACH`
- 该行为必须显式记录，不允许静默吞掉

#### 11.5 boundary 缺失
- V1 允许 boundary 为空
- 但 status 需标记 `BOUNDARY_DISABLED`

### 13. 验收标准

#### 13.1 合同层验收
满足以下条件即可认为 V1 合同成立：
1. 上下游职责边界明确，无重复规划逻辑
2. route / speed / boundary 三类输入输出被清晰定义
3. 明确区分 northbound path 合同与 southbound point 合同
4. 失败与降级策略显式，不存在静默 fallback
5. 关键参数组可配置，不写死核心阈值

#### 13.2 实施层验收

### 7. 第一批实际改动顺序

建议真实开工顺序如下：
1. **先做 WP1**：先把 `/state_estimation` 收敛出来
2. **再做 WP2**：把 Path-In / Point-Out Adapter 跑起来
3. **再做 WP3**：接通 CMU local + terrain_analysis + 底盘
4. **再做 WP4**：整理成 system launch
5. **最后做 WP5**：接任务与操作层

原因很简单：
- 没有 `/state_estimation`，FAR / CMU 接口不稳
- 没有 Adapter，northbound Path 资产无法合法接到 southbound 点式合同
- 没有 WP3，任务层接上去也只是空跑
