## 1. 当前执行目标与停止条件

### 1.1 当前执行目标
WP1 的目标不是重写底层定位算法，而是把当前仓库已经具备的定位输入，收敛成后续 FAR / CMU local / terrain_analysis 都能稳定复用的统一合同，并从旧脚本语义中独立出来：
- 通过独立 `Localization Manager` 对外统一发布 `/state_estimation`
- 锁定全局 frame 与 child frame 约定
- 让上层不再直接依赖 `/map_to_odom` 与 `/localization` 的历史细节

### 1.2 停止条件
满足以下条件即可结束 WP1，并转入 WP2：
1. `/state_estimation` 已成为对上统一合同
2. FAR / Adapter / CMU local 在设计上都只再面向 `/state_estimation`
3. `/localization` 若继续保留，仅作为短期兼容输出，不再作为主合同
4. frame 约定、异常状态与可用性标志已明确

## 5. 方案收敛

### 5.1 方案 A：最小改动方案（已完成过渡验证）
- **修改** `src/FAST_LIO_LOCALIZATION/scripts/transform_fusion.py`
  - 增加 `/state_estimation` 发布
  - 保留 `/localization` 作为短期兼容输出
- **修改** `src/FAST_LIO_LOCALIZATION/launch/localization_avia.launch`
  - 明确当前主线使用 Mid360
  - 将注释、命名或参数说明改得更贴近当前平台

**优点：**
- 改动面最小
- 复用现有工作路径最多
- 更适合当前先闭环的策略

**风险：**
- `transform_fusion.py` 继续承担过多历史语义
- 代码结构不如独立 manager 干净

### 5.2 方案 B：更干净的方案（当前采用）
- **新增** `src/greenhouse_nav/scripts/localization_manager.py`
  - 订阅 odom 与 `/map_to_odom`
  - 统一对外发布 `/state_estimation`
- **新增** `src/greenhouse_nav/launch/localization_manager.launch`
- `transform_fusion.py` 退为过渡或调试工具

**优点：**
- 分层更清晰
- 更符合后续主线长期演进

**风险：**
- 当前 WP1 的改动面更大
- 如果现阶段只是想尽快推 WP2，收益未必高于成本

### 5.3 当前采用结论
当前正式切换到 **方案 B**，但保留方案 A 的既有运行时验证结果作为过渡基线。

原因：
1. `/state_estimation` 已经证明可用，下一步重点不再是“先发出来”，而是“把主线语义独立出来”
2. 独立 `Localization Manager` 更适合作为 WP2 Adapter、后续 FAR/CMU local 的统一北向入口
3. `transform_fusion.py` 可以保留作历史兼容与调试，不再承担长期主入口职责

**关键诊断结论：**
- 第一轮 official indoor headless 使用 upstream 默认 `use_sim_time` 时，`rostopic echo` 明确提示 `simulated time is active` 且无 `/clock` 消息。
- 第二轮已将 `/use_sim_time` 显式改为 `false`，但问题仍未转化为有效消息流。
- 当前 `/gazebo` 节点虽然存在，但只暴露 `/rosout`，没有形成有效 `/clock` publisher，也没有驱动 planner/local planner 所需的数据流。
- 进一步静态核查 upstream 仿真前置后，又确认了一个更具体的阻塞：
  - `vehicle_simulator/world/indoor.world` 直接依赖 `model://indoor` 与 `librotors_gazebo_ros_interface_plugin.so`；
  - `vehicle_simulator/package.xml` 将 Gazebo model path 指向 `mesh/`；
  - 但当前仓库内 `vehicle_simulator/mesh/` 只有 `download_environments.sh`，并没有已下载环境资产。
- 因此，当前 official indoor headless 不是单纯“参数没调对”，而是 **上游 world / plugin / 环境资产前置未闭合**。
- 因此当前阻塞点已经进一步收敛到：**upstream Gazebo indoor headless 运行时本身没有真正跑出有效仿真数据流**，而不是 FAR 接口合同、包缺失、编译、launch 接线错误。

**当前结论更新：**
- `FAR -> CMU local` 的接口接线方向仍然成立。
- 但 `official indoor headless` 这条验证支路在当前 Docker/runtime 条件下，仍不足以证明 FAR 能真实产出 waypoint。
- 若继续走 official simulation 这条支路，必须先补齐 upstream 环境资产，并确认 rotors gazebo plugin 在运行环境中可解析。
- 若继续推进 E4，优先级建议调整为：
  1. 先补齐 upstream `vehicle_simulator` 的环境资产与 rotors 依赖，再看是否还需要 physics / unpause / GUI 前置；
  2. 或直接转真实 bag / 录制数据集回放，这条路径更接近最终主线。
