# 温室履带车三维导航项目执行计划书

## 1. 项目目标与 V1 作业闭环

### 1.1 场景说明
- 作业场景：崎岖温室
- 平台组成：Mid360 + 履带车 + 固定拍摄相机
- 当前约束：ROS Noetic 主线、优先复用现有底盘与点云处理链路

### 1.2 建设目标
系统需在温室田垄场景中实现以下能力：
- 稳定完成田垄间导航与沿垄前进
- 在行进过程中完成左右两侧固定点位拍摄
- 在地头区域完成低头绕弯与跨垄切换
- 支持重复作业流程执行与后续模块化扩展

### 1.3 V1 最小执行闭环
V1 聚焦“可跑通、可验证、可迭代”的最小执行闭环，任务流程如下：

```text
LocalizeAtStart
-> GoTo(Row_i_Entry)
-> FollowRowCenterline(Row_i)
-> GoTo(PhotoLeft_i_k)
-> Capture
-> ReturnTo(Row_i_Centerline)
-> GoTo(PhotoRight_i_k)
-> Capture
-> ReturnTo(Row_i_Centerline)
-> GoTo(Row_i_End)
-> HeadlandTurn(To Row_i+1_Entry)
-> Repeat
```

### 1.4 当前执行原则
- 先闭环，再增强
- 先分层，再实现
- 先锁接口，再调参数
- 先复用成熟主链，再补自研薄层

### 1.5 当前文档分工
- `".agentdocs/计划书.md"`：只负责主线决策、分层边界、阶段安排、风险与验收口径
- `".agentdocs/执行计划书.md"`：只负责当前执行中的 WP 展开；现阶段聚焦 WP1
- `".agentdocs/主线实施附录.md"`：集中保存 topic / message 基线、Adapter 合同、复用边界与长期实施参考
- `".agentdocs/补充参考.md"`：集中保存当前仓库概览、CMU 设计决策提炼、mecanum 补充工程样板

## 2. 总体执行主线与分层原则

### 2.1 主方案结论
当前主方案确定为：

**FAST-LIO2 + FAST_LIO_LOCALIZATION + FAR Planner + CMU Local Planner**

其中：
- 定位主线：FAST-LIO2 + FAST_LIO_LOCALIZATION
- 路线规划主线：FAR Planner
- 基础自主主线：CMU Local Planner
- local 感知增强候选：terrain_analysis
- 任务层：Mission Executor

### 2.2 分层原则
本项目按 CMU autonomy stack 的公开分层思想组织，核心逻辑不是“模块堆叠”，而是“层级协作”：

```text
Mission Layer
  -> Route Planner Layer
  -> Base Autonomy Layer
  -> State Estimation Layer
```

进一步展开为：

```text
Mission Executor
  -> FAR Planner
  -> CMU Local Planner
     -> terrain_analysis / collision avoidance / waypoint following
  -> FAST-LIO2 + FAST_LIO_LOCALIZATION + Localization Manager
```

### 2.3 当前项目中的层映射
- **Mission Layer**：Mission Executor
- **Route Planner Layer**：FAR Planner
- **Base Autonomy Layer**：CMU Local Planner + terrain_analysis（候选增强项）
- **State Estimation Layer**：FAST-LIO2 + FAST_LIO_LOCALIZATION + Localization Manager
- **Layer Adapter / Interface Layer**：Global-to-Local Adapter

### 2.4 方案选择依据
本项目选择当前主线的核心原因如下：

1. **FAR Planner 与 CMU local 符合同体系分层**
   - FAR 负责全局 route / visibility graph / replanning
   - CMU local 负责 waypoint mode 下的近场局部自主执行

2. **rough-terrain 能力不再依赖 MoveBase3D 旧耦合链**
   - MoveBase3D 的 rough-terrain 处理依赖 `global_planner_3d + rover_gpr + local_planner_3d`
   - 当前主线改为由 `CMU local + terrain_analysis` 承载 rough-terrain local 能力

3. **定位与 local 能力解耦更清晰**
   - FAST-LIO 系列负责状态估计
   - FAR 负责 route planner
   - CMU local 负责 local autonomy

4. **任务层可独立演进**
   - 温室作业任务不应绑死在旧多点导航插件逻辑中
   - Mission 语义应独立于具体 planner 实现

### 2.5 当前主线的总体判断
- **事实**：当前方向与 CMU 公开 autonomy stack 分层一致，且 `ground_based_autonomy_basic/noetic` 的 local topic / message / terrain_analysis 入口可从公开仓库直接确认
- **推断**：只要接口合同收敛，`FAR + CMU local` 方案可形成比 MoveBase3D 旧链更清晰的自治架构
- **未知**：当前项目最终是直接沿用 CMU noetic 原版 topic / launch，还是保留算法但做本地化封装，仍需锁定

## 3. 状态估计层（State Estimation Layer）

### 3.1 当前定位基线
当前定位基线为：

**FAST-LIO2 + FAST_LIO_LOCALIZATION**

其工程意义如下：
- FAST-LIO2 负责连续、高频、平滑的 odom 输出
- FAST_LIO_LOCALIZATION 负责在预构建点云地图内进行低频全局定位
- 初始位姿可由 RViz 手工粗初始化，也可由其他传感器或算法提供

该方案适合作为一期工程基线，即：**先设初始位姿，再让整套系统跑起来**。

### 3.2 Localization Manager（自研）定位
Localization Manager 不应被理解为“又一个定位算法”，而应被定义为：

- 接收 FAST-LIO2 高频 odom
- 接收 FAST_LIO_LOCALIZATION 全局修正
- 对外统一发布全局位姿与状态估计

### 3.3 状态估计层输出合同
当前建议输出合同为：
- `map -> odom` 或 `map -> base_link`（二选一，实施前必须锁定）
- `/state_estimation`
- 统一定位状态与可用性标志

### 3.4 当前已知问题
在温室重复田垄结构下，FAST_LIO_LOCALIZATION 面临的核心风险是：
- **重复垄结构导致的 map-based relocalization 稳定性不足**

同时，CMU 体系的 terrain map / collision avoidance 对状态估计质量敏感，因此：
- localization 失稳会直接影响 local autonomy
- registered scans 配准误差会直接污染 terrain map

### 3.5 定位升级路线
若当前基线在重复垄场景下表现不稳定，定位链优先按以下顺序升级：

1. **FAST-LIO-Localization-SC-QN**  
   定位思路：FAST-LIO2 odom + ScanContext 候选检索 + Quatro + Nano-GICP map matching。  
   适用场景：在保留现有 FAST-LIO 主链的前提下，增强候选检索与粗到细匹配能力。

2. **POINT_LIO_LOCALIZATION**  
   定位思路：POINT-LIO + small_gicp。  
   适用场景：当系统对 rough initial pose 和非结构化输入的鲁棒性要求更高时，可作为进一步升级路线。

### 3.6 本层结论
- **FAST_LIO_LOCALIZATION 是当前基线，不是最终上限**
- **Localization Manager 是输出收敛层，不是新定位算法**
- **状态估计质量会直接约束 Base Autonomy 与 terrain_analysis 的有效性**

## 4. 路线规划层（Route Planner Layer）

### 4.1 FAR Planner 的职责边界
FAR Planner 在当前方案中的职责是：
- 作为主 global / route planner
- 根据当前位置、目标点和可选导航边界生成 route
- 在已知/未知空间中做 route 级重规划
- 对外输出 ref path / route / boundary 信息

FAR Planner 在本项目中**不是兜底插件**，而是主 global planner。

### 4.2 FAR Planner 的输入输出
**输入**：
- 当前全局位姿
- 目标点 / waypoint / 作业点
- 可选导航边界 / 先验地图 / 环境信息

**输出**：
- route / ref path
- 中间 waypoint 候选
- 可选 navigation boundary

补充说明：
- 按 FAR 官方 noetic 接口，当前其 northbound 直接输出 `/way_point` 与 `/navigation_boundary`
- 因此 FAR 接入 CMU local 时，默认应优先直连，而不是再走 `/waypoints -> global_to_local_adapter`

### 4.3 Route Planner 层与 Base Autonomy 层的关系
必须明确：
- FAR 不直接承担局部避障控制
- FAR 不直接承担左右拍照动作
- FAR 不直接承担底盘执行

它的职责是：
> 负责“去哪、走哪条路、边界在哪里”

而不是：
> 负责“怎么绕这个局部障碍、这个速度怎么调、拍照时怎么停稳”

### 4.4 为什么当前不继续使用 MoveBase3D global 主链
当前不再将以下内容作为 global 主线：
- `global_planner_3d`
- `global_planning_obs_node`

原因不是其完全无效，而是：
- 它们与 `rover_gpr`、`local_planner_3d` 构成旧耦合主链
- 当前主线已切换为 `FAR + CMU local`
- 继续保留旧 global 主链会使系统长期双轨并行，增加复杂度

### 4.5 本层结论
- **FAR 是路线规划层，不是 local planner**
- **FAR 与 CMU local 应通过明确接口协作，而不是互相侵入内部逻辑**

## 5. 基础自主层（Base Autonomy Layer）

### 5.1 Base Autonomy 层的组成
当前计划书中的 Base Autonomy Layer 不是单节点，而是由以下部分组成：
- **CMU Local Planner（狭义）**：`localPlanner + pathFollower`
- **terrain_analysis（可选增强）**：提供 rough-terrain 的地形 cost / traversability 输入
- **运行模式语义**：waypoint mode、手动接管、暂停、恢复等运行态切换

因此，本层的目标不是“再做一个 planner”，而是把：
- 上层给出的 rolling waypoint / speed / boundary
- 当前位姿与局部感知

稳定收敛为底盘可执行的 `/cmd_vel`。

### 5.2 CMU Local Planner（狭义）的职责
在本计划书中，CMU Local Planner 仅指 `localPlanner + pathFollower` 这一执行组合。其职责应明确为：
1. **rolling waypoint following**
   - 跟随 `/way_point` 给出的当前局部目标
   - 处理接近目标、切换目标、终点减速等局部执行问题
2. **local collision avoidance / obstacle avoidance**
   - 默认基于 `/registered_scan` 做近场避障
   - 启用 `terrain_analysis` 后，可进一步结合 `/terrain_map` 做 rough-terrain 约束
3. **boundary-constrained local motion**
   - 在 `/navigation_boundary` 给定的局部约束下做运动裁剪
4. **局部速度与姿态约束执行**
   - 处理 look-ahead、slow down、yaw、turning、stop threshold、max speed 等参数约束
5. **输出执行控制量**
   - 最终对下游输出 `/cmd_vel`

### 5.3 CMU Local Planner 不负责的内容
为避免层间职责继续混淆，本计划书明确：CMU Local Planner **不负责**以下事项：
- 不负责全局路线搜索与重规划
- 不负责 `Path -> rolling Point` 折叠
- 不负责任务状态机、拍照流程、跳点、续跑
- 不负责定位融合或 relocalization
- 不负责 terrain map 的生成
- 不负责维护第二套并行 local planner

对应关系应固定为：
- 全局路线：`FAR Planner`
- Path-In / Point-Out 折叠：`Global-to-Local Adapter`
- 任务语义：`Mission Executor`
- 定位统一输出：`Localization Manager`
- terrain map 生成：`terrain_analysis`

### 5.4 CMU noetic 官方接口基线（已确认）
若一期直接对接 `ground_based_autonomy_basic/noetic`，其公开运行时基线为：

**输入到 CMU local：**
- `/state_estimation` -> `nav_msgs/Odometry`
- `/registered_scan` -> `sensor_msgs/PointCloud2`
- `/way_point` -> `geometry_msgs/PointStamped`
- `/speed` -> `std_msgs/Float32`
- `/navigation_boundary` -> `geometry_msgs/PolygonStamped`
- 可选 `/terrain_map` -> `sensor_msgs/PointCloud2`（当 `useTerrainAnalysis=true` 时启用）

**相关辅助接口：**
- `/map_clearing` -> `std_msgs/Float32`
- `local_planner.launch` 中预留 `terrain_analysis.launch` 的 include 入口（默认注释）
- `terrain_analysis.launch` 的执行节点为 `terrainAnalysis`

**输出：**
- `/cmd_vel` -> `geometry_msgs/TwistStamped`（README 要求转发到底盘控制器）

这意味着 stock CMU local 的 southbound 合同是：
- **单滚动 waypoint 点**
- **speed**
- **navigation boundary**

而不是直接消费一整条 `nav_msgs/Path`。官方基线汇总详见：  
`".agentdocs/主线实施附录.md"`

### 5.5 局部避障链与局部运动决策
当前主线下，局部避障不是独立外置模块，而是 CMU Local Planner 的核心职责之一。建议按以下方式理解：

```text
/state_estimation
  + /registered_scan
  + /way_point
  + /speed
  + /navigation_boundary
  + optional /terrain_map
    -> CMU Local Planner（localPlanner + pathFollower）
    -> /cmd_vel
```

其中：
- **默认输入主链** 是 `/registered_scan`
- **rough-terrain 增强输入** 是可选 `/terrain_map`
- **局部约束输入** 是 `/navigation_boundary`
- **执行目标输入** 是 `/way_point` 与 `/speed`

也就是说，当前方案并不是“没有局部避障”，而是**局部避障被明确内聚在 CMU Local Planner 内部**，而不是再单列一条自研避障链。

### 5.6 terrain_analysis 的角色定位
在当前方案中，terrain_analysis 应被理解为：
- Base Autonomy 的地形感知支撑层
- rough-terrain 场景下的重要增强项
- terrain traversability / terrain map / negative obstacle 处理的主要承载候选

它不是：
- 独立主方案
- 新的 global planner
- MoveBase3D `rover_gpr` 的简单替身
- CMU Local Planner 本体

### 5.7 terrain_analysis 的建议消息语义
基于 CMU 公开系统的设计，当前建议将 terrain_analysis 的目标语义定义为：
- 输出 `/terrain_map`
- 消息类型为 `sensor_msgs/PointCloud2`
- terrain map 中每个点不仅表示几何位置，还应携带可通行性 / cost 语义
- 若沿用 CMU 方案，可优先参考 **`pcl::PointXYZI` 中 intensity 存 cost** 的表达方式

同时建议预留两类运行机制：
- **terrain map clearing / reset**
  - 支持局部清图或全局重置
  - 典型场景：重定位后、漂移累积后、误注册污染 terrain map 后
- **negative obstacle 策略**
  - 预留 `noDataObstacle` 一类开关
  - 将无数据区按不可通行或高风险区域处理

### 5.8 terrain_analysis 的当前状态
官方 noetic 基线的执行入口已明确：
- `src/terrain_analysis/launch/terrain_analysis.launch`
- `pkg=terrain_analysis`、`type=terrainAnalysis`、`name=terrainAnalysis`
- `src/local_planner/launch/local_planner.launch` 提供 include 位与 `useTerrainAnalysis` 开关

当前仍未锁定的是：
- 本项目是否直接复用该原版包结构
- 是否移植 `autonomy_stack_mecanum_wheel_platform` 中的实现/参数基线
- 我们自己的 launch 编排、命名空间和 topic remap 方式

因此现阶段应将其定义为：

**官方入口已知、但项目化接入方式尚未锁定的 Base Autonomy 增强项**

### 5.9 地势分析候选实现优先级
当前更适合纳入新主线的候选承载体为：

1. **`ground_based_autonomy_basic` 中的 terrain_analysis**
2. **`autonomy_stack_mecanum_wheel_platform` 中的 `terrainAnalysis.cpp` 及其配套 launch/参数逻辑**
3. **MoveBase3D 的 GPR 地势分析链（仅作为补充参考，不作为主线）**

### 5.10 CMU local 与 DWA 的边界
当前计划书不将“DWA 更稳 / CMU local 更稳”作为先验结论，而采用如下判断方式：
- DWA 更像成熟的局部速度采样器
- CMU local 更像 rough-terrain 场景下的 base autonomy 层
- 两者稳定性不能只按算法名比较，必须结合：
  - 输入语义
  - terrain map 是否启用
  - 运动模型
  - look-ahead / speed / yaw 参数
  - 状态估计质量

### 5.11 Base Autonomy 当前需要重点确认的算法点
当前真正需要收敛的不是“是否用某个名字更响的算法”，而是以下算法与运行点：
1. waypoint mode 下的局部目标滚动规则
2. `/registered_scan` 与 `/terrain_map` 的使用边界
3. navigation boundary 对 local motion 的约束方式
4. negative obstacle 处理策略
5. terrain map clearing / reset 触发条件
6. local planner 的速度、look-ahead、yaw、边界参数组
7. 状态估计漂移对 terrain map 与 local 跟随的影响

### 5.12 MoveBase3D GPR 地势分析链在本层的位置
MoveBase3D 原有 rough-terrain 链可概括为：

```text
global_planner_3d
  -> tree_tra / global_path
  -> rover_gpr
  -> /surf_predict_pub
  -> local_planner_3d
```

该链条在当前计划书中仅作为：
- 历史实现路径
- 对比实验 baseline
- 问题回溯参考

不再作为当前主线执行依据。

### 5.13 本层结论
- **Base Autonomy 层不等于单独一个 planner 节点，而是 `CMU Local Planner + optional terrain_analysis + 运行模式语义` 的组合**
- **CMU Local Planner（狭义）已经包含局部避障、局部目标跟随和局部运动决策，不需要再平行自研一条 local 避障主链**
- **terrain_analysis 是地形语义增强输入，不是 CMU Local Planner 本体，也不是新的 global planner**
- **当前最大缺口仍是 southbound 合同收敛、terrain_analysis 项目接入方式，以及参数基线锁定**

## 6. 任务层（Mission Layer）

### 6.1 Mission Executor（自研）定位
Mission Executor 的角色不是“又一个 planner”，而是：
- 管理作业锚点序列
- 管理事件触发与任务状态流转
- 将温室作业流程翻译成 Route Planner 可消费的作业目标

### 6.2 任务锚点模型
V1 采用“锚点队列 + 事件触发”，不引入复杂行为树或任务图系统。

锚点示例如下：
- `Row1_Entry`
- `Row1_LeftPhoto_1`
- `Row1_CenterRecover_1`
- `Row1_RightPhoto_1`
- `Row1_CenterRecover_2`
- `Row1_Exit`
- `Headland_Turn_1`

### 6.3 任务状态流转建议
当前建议的任务状态流转包括：
- 到达目标锚点
- 触发拍照
- 拍照完成确认
- 回中心线恢复
- 地头转向
- 切换到下一行
- 异常中断 / 重试 / 跳点 / 续跑

### 6.4 为什么 MoveBase3D 多点导航不能替代 Mission 层
MoveBase3D 可复用的是：
- 单目标点录入
- 多目标点管理
- 巡点交互与可视化

但不能直接替代：
- 行点、拍照点、回中心线点、地头点的任务编排
- 到点拍照触发与拍后恢复
- 地头掉头与跨垄切换
- 异常中断、跳点、重试、续跑

### 6.5 本层结论
- **Mission 层必须独立存在**
- **MoveBase3D 的多点导航仅能作为交互资产，不能直接承担温室作业任务逻辑**

## 7. 层间接口合同（Integration Contracts）

### 7.1 Mission Layer -> Route Planner Layer
Mission 层对 FAR 的输出应至少包括：
- 当前任务目标点
- 目标点类型（行点 / 拍照点 / 地头点）
- 任务速度模式请求
- 可选作业边界或约束

### 7.2 Route Planner Layer -> Base Autonomy Layer
该层由 **Global-to-Local Adapter（自研）** 承担。

其职责不是“复杂中台”，而是薄接口层：
- FAR path -> rolling local guidance
- FAR boundary -> local boundary
- Mission 速度模式 -> local speed

若 southbound 直接对接 stock `ground_based_autonomy_basic/noetic`，则最终发布形态应收敛为：
- `/way_point`（`geometry_msgs/PointStamped`）
- `/speed`（`std_msgs/Float32`）
- `/navigation_boundary`（`geometry_msgs/PolygonStamped`，可选）

也就是说，Adapter 内部可以维护 `Path` 形式的滚动窗口用于裁剪、调试和监控，但不能把它误写成 CMU 原生 southbound 输入合同。

Adapter 的 V1 接口合同已单独收敛，详见：  
`".agentdocs/主线实施附录.md"`

### 7.3 State Estimation Layer -> Route / Base Autonomy
状态估计层对上层至少应提供：
- 当前全局位姿
- 当前里程计与姿态连续性
- 可用 frame 约定
- 状态可用性标志

### 7.4 terrain_analysis -> Base Autonomy
若启用 terrain_analysis，建议形成以下接口合同：
- 输出 `/terrain_map`
- terrain map 使用带 cost 语义的点云表达
- 可优先参考 `PointXYZI + intensity=cost` 的语义
- 支持 clear / reset / map clearing 机制
- 支持 negative obstacle 的参数化处理

### 7.5 到达判据与切换条件
当前计划书要求后续在实施前锁定以下判据：
- local waypoint 到达条件
- route waypoint 切换条件
- 拍照完成确认条件
- 地头转向完成条件
- 恢复成功条件
- 异常中断后的重试/跳点规则

### 7.6 当前最需要补齐的接口缺口
当前文档中最不清晰、必须优先补齐的不是“算法名称”，而是：
1. Localization Manager 的最终输出合同
2. Global-to-Local Adapter 的北向 path 合同如何折叠为南向 `/way_point` 合同
3. terrain_analysis 的项目接入方式、参数基线与 clear/reset 策略
4. Mission 拍照动作与导航状态的交互接口
5. CMU local 的 look-ahead / yaw / speed / boundary 参数基线

## 8. 复用资产、历史链路与非复用边界

### 8.1 主线强相关复用清单（必须吸收）
结合 `autonomy_stack_mecanum_wheel_platform` 与当前仓库已有资产，对当前主线最需要真正吸收的内容收敛如下：

1. **统一 `/state_estimation` 合同**
   - 保留当前 `FAST_LIO_LOCALIZATION + transform_fusion` 基线
   - 增加 `Localization Manager`，把现有 `/map_to_odom` / `/localization` 收敛为对上层统一可用的 `/state_estimation`
   - 目的：满足 FAR / CMU local / terrain_analysis 的统一上游状态输入

2. **CMU southbound 点式合同**
   - 明确 southbound 目标接口为：`/way_point`、`/speed`、`/navigation_boundary`
   - Adapter 内部可以保留 `Path` 窗口，但 southbound 不再写成 `Path` 直通 local
   - 目的：让 `FAR + CMU local` 真正按 stock CMU 语义对接

3. **CMU local 的双节点运行时结构**
   - 吸收 `localPlanner + pathFollower` 的职责拆分
   - 吸收其参数组织思路：look-ahead、slow down、goal clear、path scale、speed、yaw 等
   - 目的：替换旧 `local_planner_3d` 的耦合式主线地位

4. **terrain_analysis 的主链接法**
   - 一期将 `terrain_analysis` 作为 rough-terrain 主线增强项接入
   - 二期评估 `terrain_analysis_ext` 与 `sensor_scan_generation` 是否纳入
   - 目的：用 CMU 地形链替代旧 `rover_gpr` 主线角色

5. **system launch 编排方式**
   - 参考 `system_real_robot_with_route_planner` 这一类入口组织新的温室系统启动链
   - 将定位、terrain、local、FAR、底盘执行、可视化组织成正式系统入口
   - 目的：避免后续实施仍停留在临时 launch 拼接层面

### 8.2 当前仓库中建议继续保留的复用资产
以下内容不需要推倒重来，应继续纳入新主线：
1. `FAST_LIO_LOCALIZATION + transform_fusion` 的定位基线能力
2. MoveBase3D 的 RViz 单目标点工具
3. MoveBase3D 的 RViz 多目标点管理面板
4. `waypoint_generator` 一类 `Path` 型 northbound 交互资产
5. 现有底盘执行层与 `cmd_vel` 外围链路
6. 现有 Livox + FAST_LIO 传感链路

### 8.3 MoveBase3D 历史 rough-terrain 链补充说明
MoveBase3D 在原方案中并非“没有地势分析”，而是存在一条与其旧规划链强耦合的地势处理路径。该部分保留为：
- 历史实现说明
- A/B baseline 参考
- 设计回溯依据

但不再作为当前主线执行路径。

### 8.4 非复用边界
以下内容不再作为当前项目主线复用对象：
- `global_planner_3d`
- `global_planning_obs_node`
- `rover_gpr`
- `local_planner_3d`
- MoveBase3D 自带规划执行闭环
- `autonomy_stack_mecanum_wheel_platform` 的 exploration planner 主路径
- `autonomy_stack_mecanum_wheel_platform` 的整套 ROS2 Jazzy 运行时框架

### 8.5 处理原则
对当前仓库与外部参考能力的总体策略为：

**定位保留本仓基线，local 吸收 CMU 结构，terrain 转向 CMU 主链，交互继续复用 MoveBase3D，系统编排参考 mecanum。**

## 10. 当前未决项、风险与升级路线

### 10.1 当前未决项
1. Localization Manager 最终发布 `map->odom` 还是 `map->base_link`
2. Global-to-Local Adapter 的北向 route/path 合同已形成，但 southbound 是否完全镜像 CMU 官方 `/way_point` / `/speed` / `/navigation_boundary` 仍需锁定
3. terrain_analysis 官方入口已知，但本项目采用原版包、移植 `autonomy_stack_mecanum_wheel_platform`，还是做本地封装，仍需锁定
4. CMU Local Planner 的参数基线（look-ahead / yaw / cost / noDataObstacle / clear 策略）需要仿真或实车收敛
5. Mission 拍照动作与导航状态的最终交互合同

### 10.2 当前风险
- 重复垄结构下 map-based relocalization 稳定性不足
- FAR 与 CMU Local Planner 的接口适配存在额外工程成本
- `terrain_analysis` 当前仅完成方案级纳入，项目接入方式与参数基线尚未锁定
- 地头绕弯和狭窄空间下局部通行能力需要现场验证
- 固定相机拍照点与导航锚点之间可能存在时序耦合问题
- localization 漂移会直接影响 terrain map 与 local autonomy

### 10.3 升级路线
- **定位升级**：FAST-LIO-Localization-SC-QN -> POINT_LIO_LOCALIZATION
- **Base Autonomy 增强**：terrain_analysis 接入与参数收敛
- **任务层增强**：重试、跳点、恢复、异常续跑
- **长期备选**：ROS2 迁移后评估 vox_nav / mesh_navigation 等框架级替代路线

## 12. 结论

本项目当前执行主线明确如下：
- **Mission Layer**：Mission Executor
- **Route Planner Layer**：FAR Planner
- **Base Autonomy Layer**：CMU Local Planner + terrain_analysis（候选增强项）
- **State Estimation Layer**：FAST-LIO2 + FAST_LIO_LOCALIZATION + Localization Manager
- **Layer Adapter**：Global-to-Local Adapter

因此，当前计划书不再按“模块平铺”组织，而按“层级协作”组织。后续执行重点也不再是继续比较旧链算法名称，而是优先收敛：
1. 层级职责边界
2. 层间接口合同
3. terrain_analysis 项目接入方案
4. Mission 与导航动作的闭环关系

这是当前方案能否真正落地的抓手。
