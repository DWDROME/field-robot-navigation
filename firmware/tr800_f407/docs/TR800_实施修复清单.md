# TR800 实施修复清单

本文档是 TR800 第一阶段修复的实施入口，目标是把当前工程从“功能堆叠式代码”收敛为“可定位、可验证、可回滚”的嵌入式控制主线。

当前第一阶段只保留 `SERIAL + RC` 两个外部控制源。云台、PS2、未启用 CAN RX、MAVLink 发送、历史多车型泛化不进入第一阶段主线。

## 1. 现状目录定位

当前工作区根目录：

`TR800_F407/`

现有目录职责：

| 路径 | 当前职责 | 当前问题 |

第一阶段实施原则：

- 可以先不拆文件，但职责必须先在代码里收口。
- 不新增静默兜底，不伪造“成功状态”。
- 不恢复云台、PS2、CAN RX、历史多车型控制入口。
- 所有运动命令只允许在一个任务上下文生效。
- 允许保留全局状态与全局快照，但同一控制语义只能有一个写者。

### 2.1 第一阶段代码组织原则

这一阶段不追求“大框架”，只追求主链路收口。

保留为全局是允许的：

- `TR800_Runtime`
- `MOTOR_A/B`
- 编码器反馈
- `g_serial_cmd`
- `g_rc_cmd`

不允许继续作为多上下文共享可写控制总线的是：

- `Move_X`
- `Move_Y`
- `Move_Z`

目标约束：

- `SERIAL` 路径只更新串口命令快照。
- `RC` 路径只更新遥控命令快照。
- `runtime` 只更新系统状态、fault、alive。
- 只有 `Balance_task` 可以把快照仲裁为本周期生效命令，并继续生成电机目标和 PWM。

## 3. 主链路职责分布

### 3.1 启动与任务

当前任务创建位置：

- `USER/main.c:16-27` 启动系统并开启 FreeRTOS。
- `USER/main.c:30-42` 创建 `Balance_task`、`MPU6050_task`、`show_task`、`led_task`、`data_task`、`RC_task`。

当前优先级：

| 任务 | 位置 | 当前优先级 | 建议职责 |
|---|---|---:|---|
| `Balance_task` | `BALANCE/balance.c` | `BALANCE_TASK_PRIO=4` | 100Hz 主控制环，唯一执行速度闭环和 PWM 输出。 |
| `RC_task` | `HARDWARE/usartx.c` | `RC_TASK_PRIO=5` | 读取 RC 输入，生成 RC 命令快照，不直接压过主控制环。 |
| `data_task` | `HARDWARE/usartx.c` | `DATA_TASK_PRIO=4` | 当前只做 UART4 遥测发送，后续演进为 `comm_task`。 |
| `show_task` | `BALANCE/show.c` | `SHOW_TASK_PRIO=3` | OLED 显示，低频刷新，不参与控制决策。 |
| `MPU6050_task` | `HARDWARE/MPU6050.c` | `MPU6050_TASK_PRIO=3` | IMU 采样。 |
| `led_task` | `HARDWARE/LED.C` | `LED_TASK_PRIO=3` | LED 状态提示，不写控制状态。 |

修复要求：

- `Balance_task` 是运动输出唯一主环，优先级必须高于 `RC_task` 和 `data_task`。
- `RC_task` 不能直接执行阻塞串口发送。
- 串口 ISR 不能直接写 `Move_X/Move_Y/Move_Z`。
- 所有任务创建需要检查返回值，失败时进入可见 fault 状态。

当前频率证据：

- `Balance_task`：100Hz，`BALANCE/balance.c:249-256`
- `MPU6050_task`：100Hz，`HARDWARE/MPU6050.c:42-57`
- `data_task`：40Hz，`HARDWARE/usartx.c:595-608`
- `RC_task`：IBUS 50Hz / SBUS 80Hz，`HARDWARE/usartx.c:1548-1552`
- `show_task`：10Hz，OLED 实刷约 2Hz，`BALANCE/show.c:20-25`、`BALANCE/show.c:79-85`

推荐优先级与频率关系：

| 任务 | 当前优先级/频率 | 建议优先级/频率 | 调整理由 |
|---|---:|---:|---|
| `Balance_task` | `4 / 100Hz` | `5 / 100Hz` | 主控制环必须是最终执行者，不能被输入任务压住。 |
| `RC_task` | `5 / 50-80Hz` | `4 / 50-80Hz` | RC 是输入生产者，不应高于主控制环。 |
| `data_task` -> `comm_task` | `4 / 40Hz` | `3 / 40-50Hz` | 串口解析和遥测不应抢控制主环。 |
| `MPU6050_task` | `3 / 100Hz` | `3 或 4 / 100Hz` | 若当前仅用于诊断与启动校准，不必高于主控制环。 |
| `show_task` | `3 / 10Hz` | `2 / 10Hz`，实刷 `2Hz` | UI 只服务人眼调试，不应带副作用。 |
| `led_task` | `3 / 低频` | `1 / 低频` | 状态灯最低即可。 |

当前任务细账：

| 任务 | 当前职责 | 当前阻塞点/副作用 | 当前共享状态问题 | 第一阶段处理 |
|---|---|---|---|---|
| `Balance_task` | 编码器、runtime、逆解、PI、PWM | 无明显外设忙等，但读的是共享控制量 | 直接读取被 ISR / RC / runtime 共同写入的 `Move_X/Y/Z` | 保留为唯一运动输出入口 |
| `RC_task` | RC 读取、模式请求、写运动命令 | 可能夹带云台阻塞发送 | 通过 `rc_loop_control()` 直接写 `Move_X/Y/Z` | 保留，但只生 RC 命令快照 |
| `data_task` | 遥测打包与 UART4 发送 | `USART4_SEND()` 逐字节忙等发送 | 与串口接收状态脱节 | 重命名/演进为 `comm_task` |
| `MPU6050_task` | MPU6050 采样、启动校准计数 | 软件 I2C + `delay_us()` 忙等 | 当前 `Deviation_Count` 被拿去当 runtime boot tick | 保留采样，移除 boot delay 所有权 |
| `show_task` | 显示、蜂鸣器、电压采样、切页 | 100 次 ADC 采样、切页清屏、刷新 OLED | 混入非显示职责 | 保留显示，移出蜂鸣器/采样副作用 |
| `led_task` | LED 闪烁 | 无大阻塞 | 顺手写 `rc_alive=0` | 保留闪灯，移除其他状态写入 |

### 3.2 启动延迟与状态来源统一

当前存在两套启动/允许控制计时：

- `Time_count` 在 `Balance_task` 中递增：`BALANCE/balance.c:249-258`
- `Deviation_Count` 在 `MPU6050_task` 中递增：`HARDWARE/MPU6050.c:42-52`
- `UART4_IRQHandler()` 用 `Time_count<CONTROL_DELAY` 拒绝控制：`HARDWARE/usartx.c:491-500`
- `tr800_runtime_update()` 用 `Deviation_Count` 判断 boot delay：`BALANCE/balance.c:269`、`BALANCE/system.c:146-181`

这会造成：

- 启动允许控制的时间基不唯一
- 串口接收路径与 runtime 状态路径对“是否已启动完成”的判断不一致

修复要求：

- 第一阶段只保留一个启动延迟计时来源，建议统一到 `TR800_Runtime.boot_ticks`
- `UART4_IRQHandler()` 不再自行判断 boot delay
- `MPU6050_task` 不再承担 runtime 启动状态推进职责

### 3.3 控制源仲裁

当前状态结构：

- `BALANCE/system.h:75-101` 定义 `TR800_SystemState`、`TR800_ControlMode`、`TR800_RuntimeStatus`。
- `BALANCE/system.c:90-104` 定义运行时状态和串口/遥控超时。
- `BALANCE/system.c:164-215` 根据启动延迟、使能、低压和 requested mode 更新 active mode。

当前问题：

- `UART4_IRQHandler()` 在 ISR 内写模式和运动命令。
- `RC_task()` 在任务内也写模式和运动命令。
- `tr800_runtime_note_serial_rx()` 和串口命令更新不同步，可能产生旧速度残留。
- `tr800_runtime_update()` 当前只是状态更新和停机清零，尚未成为唯一控制仲裁中心。

目标职责：

| 模块 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|
| UART4 ISR | 字节流 | 完整帧缓存、时间戳、帧有效标志 | 禁止写 `Move_X/Y/Z`，禁止请求模式。 |
| RC 输入 | IBUS/SBUS 通道 | 归一化 RC 命令、时间戳 | 禁止直接写 PWM。 |
| 控制仲裁 | SERIAL 命令、RC 命令、alive 状态 | `active_mode`、当前命令 | 禁止散落在多个任务。 |
| 运动主环 | 当前命令 | 左右履带目标、PWM | 禁止读取未仲裁的原始输入。 |

建议命令快照结构：

```c
typedef struct
{
    float x;
    float y;
    float z;
    uint32_t rx_ms;
    uint16_t seq;
    uint8_t valid;
} TR800_CmdSnapshot;
```

建议仲裁流程：

```text
UART4 ISR / USART2 ISR
  -> 原始帧/原始通道
  -> g_serial_cmd / g_rc_cmd
  -> Balance_task
  -> active command
  -> Drive_Motor()
  -> PWM
```

而不是：

```text
ISR / RC task
  -> 直接写 Move_X/Y/Z
```

## 5. 分阶段修复清单

### P0：先修运动状态入口

目标：消除移动状态抢写和旧速度残留。

实施项：

### P1：修履带两侧同时移动链路

目标：确认“左右履带不能同时动”是软件输出、反馈保护还是机械卡滞。

关键代码：

- `BALANCE/balance.c:217-225`：`Drive_Motor()` 根据 `Vx/Vz` 计算左右履带目标。
- `BALANCE/balance.c:274-291`：主环更新 runtime、计算目标和 PI。
- `BALANCE/balance.c:335-345`：PWM 限幅、保护计数、输出。
- `BALANCE/balance.c:363-367`：`Set_Pwm()` 调用 `Apply_Motor_Pwm_Output()`。
- `BALANCE/balance.c:42-86`：电机方向和 PWM 寄存器写入。
- `HARDWARE/motor.h:7-32`：A/B 电机 PWM 与方向引脚映射。
- `BALANCE/balance.c:756-795`：编码器速度读取和 A/B 极性。

实施项：

- [ ] 增加 `Drive_Motor()` 输入输出诊断：`Move_X`、`Move_Z`、`MOTOR_A.Target`、`MOTOR_B.Target`。
- [ ] 增加 PI 输出诊断：`MOTOR_A.Encoder`、`MOTOR_B.Encoder`、`MOTOR_A.Motor_Pwm`、`MOTOR_B.Motor_Pwm`。
- [ ] 检查 `Stop_Request_Active()` 是否在有目标速度时误触发。
- [ ] 检查 `Turn_Off()` 是否因 `Voltage`、`EN`、`Flag_Stop` 误清 PWM。
- [ ] 检查 `hall_stop` 是否因单侧编码器反馈异常导致保护停机。
- [ ] 用开环测试区分电机/驱动/机械问题和闭环软件问题。

验收：

- [ ] 空载开环：A/B 两路 PWM 同时输出，方向引脚符合预期。
- [ ] 空载闭环：`Move_X>0, Move_Z=0` 时 A/B 目标同向，编码器反馈同向。
- [ ] 原地转向：`Move_X=0, Move_Z!=0` 时 A/B 目标反向。
- [ ] 若 PWM 同时输出但一侧不动，判定为驱动/线束/机械/电机侧问题，不继续改控制算法。

实施项：

### P3：删除或隔离非主线功能

目标：减少功能重叠，避免历史路径误触发。

实施项：

- [ ] 云台：删除或编译隔离 `Yuntai_*` 数据和发送逻辑；用户当前不需要云台。
- [ ] CAN RX：保留初始化可以讨论，但 `CAN1_RX0_IRQHandler()` 内写 `Move_X/Y/Z` 必须删除或永久编译隔离。

## 8. 实施顺序

建议按以下顺序执行，每一步单独构建和实车验证：

1. 维护 `docs/TR800_通信协议.md`，确保 UART4 控制帧、遥测帧、IBUS/SBUS 与当前编译配置一致。
2. 重构 UART4 ISR：只收帧，不写模式和运动命令。
3. 收缩 RC 路径：`RC_task` / `rc_loop_control()` 只产生 RC 命令快照。
4. 统一控制仲裁点：`SERIAL + RC -> active command -> Drive_Motor()`。
5. 统一启动延迟计时来源和停机归零归属。
6. 增加履带诊断字段：目标、编码器、PWM、fault、active mode。
7. 用串口工具验证 A/B 两侧目标和 PWM 是否同时出现。
8. 修 OLED：限频、禁止渲染中清屏、降低 ADC 采样成本、拆出蜂鸣器副作用。
9. 删除或隔离云台、旧 `Motor_run()`、CAN RX 运动入口、MAVLink 阻塞发送。
10. 开启 FreeRTOS 栈溢出、malloc failed hook、任务心跳与超周期统计。
11. 维护 `docs/TR800_控制链路.md` 和新增 `docs/TR800_实车验证清单.md`。

## 9. 停止条件

遇到以下情况暂停继续改代码，先回到证据定位：

- A/B 目标速度同时非零，但只有一侧 PWM 非零。
- A/B PWM 同时非零，但只有一侧履带转动。
- `Flag_Stop=1`、`fault_flags!=0` 或 `EN=0` 导致所有 PWM 被清零。
- OLED 卡死同时 `Balance_task` 心跳正常。
- 串口控制帧 checksum 正确，但 runtime 没有进入 `SERIAL`。
- RC alive 正常，但模式无法进入 `RC`。

本项目从外部参考中明确学习的内容：

- 分层：`bsp -> modules -> application`
- 轻 ISR：中断只完成接收与通知，不直接写业务控制量
- 命令快照：输入源各自保留快照，最终命令由主环统一生效
- 在线/离线：控制失联后由控制链路统一归零
- 任务纪律：主控制环高于输入与显示任务

本项目明确不学习的内容：

- 为了“像框架”引入大规模消息总线或复杂 app 层
- 让显示、遥测、云台、调试功能与主控制环并列争抢控制语义
- 继续扩大 `usartx.c` 或 `system.h` 这种跨职责聚合文件
