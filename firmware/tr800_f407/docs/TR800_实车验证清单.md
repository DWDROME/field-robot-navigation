# TR800 实车验证清单

本文档只服务 TR800 第一阶段主线验证。

目标不是“把车跑起来就算完”，而是按当前最容易出问题的链路逐项确认：

- 启动延迟是否一致
- 使能与 fault 是否真的能拦住输出
- `SERIAL` 与 `RC` 是否会抢控制
- 左右履带是否同时收到目标、PWM、反馈
- OLED/遥测是否会拖慢主控制环

## 1. 验证前提

开始前确认：

- 当前固件与文档一致：
  - `IBUS_EN = 1`
  - `SBUS_EN = 0`
  - `PROTOCOL_25 = 0`
  - `TR800_MOTOR_TELEMETRY_DEBUG = 1`
- 上位机工具使用当前版本：
  - `tools/tr800_serial_analyzer.py`
- 已知当前控制链路目标：
  - `SERIAL/RC -> 命令快照 -> Balance_task -> Drive_Motor -> PWM`

建议准备：

- 串口上位机一台
- 遥控器一套
- 履带离地的空载支撑架
- 万用表或电源显示
- OLED 可见

## 2. 观测点

验证时至少同时观测以下 4 类信号：

1. 外部输入
   - UART4 控制帧
   - 遥控器输入

2. 运行状态
   - `Flag_Stop`
   - `system_state / requested_mode / active_mode`
   - `EN`
   - `fault_flags`

3. 电机链路
   - `MOTOR_A.Target`
   - `MOTOR_B.Target`
   - `MOTOR_A.Motor_Pwm`
   - `MOTOR_B.Motor_Pwm`
   - `MOTOR_A.Encoder`
   - `MOTOR_B.Encoder`

4. 用户侧反馈
   - OLED 页面
   - 串口遥测

## 3. 串口工具建议命令

当前固件编译配置下，推荐先用电机诊断模式观察：

```bash
python3 tools/tr800_serial_analyzer.py --port <串口> --baud 115200 --diag-raw
```

发送前进命令：

```bash
python3 tools/tr800_serial_analyzer.py \
  --port <串口> \
  --baud 115200 \
  --diag-raw \
  --send-x 0.20 \
  --send-z 0.00 \
  --send-duration 3 \
  --send-rate 20
```

发送原地转向命令：

```bash
python3 tools/tr800_serial_analyzer.py \
  --port <串口> \
  --baud 115200 \
  --diag-raw \
  --send-x 0.00 \
  --send-z 0.50 \
  --send-duration 3 \
  --send-rate 20
```

若后续切到 RC 诊断遥测，再用：

```bash
python3 tools/tr800_serial_analyzer.py --port <串口> --baud 115200 --diag-rc
```

## 4. 验证步骤

### 4.1 上电与启动延迟

目的：

- 确认启动延迟期间不会提前响应控制命令

步骤：

1. 上电，不操作遥控器和上位机
2. 观察 OLED 与串口遥测
3. 在上电后 10 秒内发送 UART4 前进命令
4. 观察 `Flag_Stop`、模式状态、电机目标与 PWM

通过标准：

- 启动延迟期间 PWM 始终为 0
- 启动延迟期间即使收到串口命令，也不会产生有效运动输出
- 启动延迟结束后，系统状态进入可运行状态

失败信号：

- 上电几秒内已出现非零 PWM
- 串口路径和 runtime 路径对“可运行”的判断不一致

### 4.2 使能开关与 fault

目的：

- 确认 `EN` 和 fault 能一致拦截输出

步骤：

1. 系统进入可运行状态
2. 发送串口前进命令
3. 在命令持续期间切断/关闭使能
4. 再恢复使能

通过标准：

- 使能关闭后，A/B PWM 立即归零
- OLED 与遥测能看到 stop/fault 状态
- 恢复使能后，系统按当前主链路规则恢复，不出现旧命令残留

失败信号：

- 使能关闭时仍有 PWM 输出
- 使能恢复后车辆直接沿用关闭前旧命令

### 4.3 串口前进

目的：

- 确认 `SERIAL` 前进命令能让 A/B 两侧同时进入同向运动

步骤：

1. 车辆空载离地
2. 发送 `x > 0, z = 0`
3. 观察遥测中的：
   - `x_mm_s`
   - `rawA/rawB`
   - `pwmA/pwmB`
   - `encA/encB`

通过标准：

- `MOTOR_A.Target`、`MOTOR_B.Target` 同号且非零
- `pwmA`、`pwmB` 同号且非零
- `encA`、`encB` 同向变化

失败分流：

- 目标非零但单侧 PWM 为 0：软件链路问题
- PWM 同时非零但单侧编码器不动：驱动/电机/线束/机械问题

### 4.4 串口原地转向

目的：

- 确认 `SERIAL` 转向命令能让 A/B 两侧目标反向

步骤：

1. 车辆空载离地
2. 发送 `x = 0, z != 0`
3. 观察目标、PWM、编码器

通过标准：

- `MOTOR_A.Target` 与 `MOTOR_B.Target` 反号
- `pwmA` 与 `pwmB` 反号
- `encA` 与 `encB` 反向变化

失败信号：

- 两边目标没有反向
- 两边 PWM 同向

### 4.5 RC 接管

目的：

- 确认 RC 路径能接管控制，但不会和串口抢写最终命令

步骤：

1. 让串口持续发送前进命令
2. 将 RC 模式选择拨到接管位置
3. 摇动 RC 前进/转向
4. 观察 `requested_mode / active_mode` 与车辆动作

通过标准：

- RC 接管后，车辆按 RC 命令动作
- 串口不再继续直接改当前生效运动命令
- 模式切换状态可从 OLED/遥测看见

失败信号：

- RC 与串口来回抢动作
- 模式显示为 RC，但实际仍跟串口走

### 4.6 RC 释放回 SERIAL

目的：

- 确认从 RC 释放回串口时不会复用旧速度

步骤：

1. RC 接管期间让串口侧保持在线
2. RC 释放/退出接管
3. 观察切回 `SERIAL` 后的第一拍动作

通过标准：

- 切回 `SERIAL` 后只使用最新有效串口帧
- 不出现“突然跳到几秒前旧速度”的动作

失败信号：

- 切换瞬间动作异常
- 切回串口后先执行旧命令，再收到新命令才恢复正常

### 4.7 串口超时停机

目的：

- 确认停止发送串口后会按超时规则归零

步骤：

1. 串口持续发送前进命令 3 秒
2. 停止发送
3. 观察目标、PWM、模式状态

通过标准：

- 超时后当前生效命令归零
- PWM 归零
- 状态进入 `READY` 或 `OFF` 对应状态

失败信号：

- 停止发送后车辆继续跑
- 模式切掉了但输出没归零

### 4.8 OLED 干扰验证

目的：

- 确认显示不会拖垮控制主线

步骤：

1. 在串口前进或 RC 前进状态下持续切页
2. 观察 OLED 是否黑屏、卡顿
3. 同时观察车辆输出是否出现明显抽动或停顿

通过标准：

- OLED 切页可有短时视觉刷新，但不影响控制连续性
- `Balance_task` 主控制不因显示刷新失控

失败信号：

- 切页时车辆明显抽动
- OLED 卡死同时控制也异常

### 4.9 低电压保护

目的：

- 确认低压时 fault 和停机逻辑一致

步骤：

1. 在安全条件下模拟低压或使用可控电源下调
2. 观察 `voltage_v`、fault、PWM

通过标准：

- 电压低于阈值后，fault 生效
- PWM 归零
- OLED/遥测可见低压状态

## 5. 推荐记录格式

每次实车验证建议记录：

| 项目 | 输入条件 | 观察结果 | 结论 |
|---|---|---|---|
| 启动延迟 | 上电 10 秒内串口前进 | PWM 是否为 0 | 通过/失败 |
| 串口前进 | `x=0.2,z=0` | A/B 目标、PWM、编码器 | 通过/失败 |
| 串口转向 | `x=0,z!=0` | A/B 是否反向 | 通过/失败 |
| RC 接管 | RC 开关拉高 | 模式与动作是否一致 | 通过/失败 |
| RC 释放 | 从 RC 回到 SERIAL | 是否有旧命令残留 | 通过/失败 |
| 串口超时 | 停止发送 | 是否停机 | 通过/失败 |
| OLED 干扰 | 连续切页 | 是否影响控制 | 通过/失败 |

## 6. 失败归因优先顺序

出现问题时，优先按以下顺序归因：

1. 先看目标是否正确
   - `MOTOR_A.Target`
   - `MOTOR_B.Target`

2. 再看 PWM 是否正确
   - `pwmA`
   - `pwmB`

3. 再看编码器是否反馈
   - `encA`
   - `encB`

4. 最后再看机械/线束/驱动侧

不要一开始就把问题归因到 PID、编码器极性或机械卡死。  
先把“命令 -> PWM -> 反馈”链路一段一段证实。

## 7. 当前最重要的通过标准

第一阶段是否算真正过关，核心只看这 5 条：

- `SERIAL` 前进时 A/B 两侧同时输出
- `SERIAL` 转向时 A/B 两侧反向输出
- `RC` 接管时不会和 `SERIAL` 抢写最终命令
- 停止发送命令后系统能超时停机
- OLED/显示路径不会拖垮控制主线
