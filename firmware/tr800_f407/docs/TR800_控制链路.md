# TR800 控制链路

本文档只描述 TR800 第一阶段主控制链路。

第一阶段只保留两个外部控制源：

- `SERIAL`
- `RC`

目标不是重做框架，而是把当前“多处抢写运动状态”的代码收敛成“单一生效入口”的控制链路。

## 1. 当前链路现状

当前工程中，最终运动控制量 `Move_X/Move_Y/Move_Z` 不是单一来源，而是被多个上下文共同写入：

- `UART4_IRQHandler()` 直接写串口命令：`HARDWARE/usartx.c:491-517`
- `rc_loop_control()` 直接写遥控命令：`BALANCE/balance.c:720-732`
- `tr800_runtime_update()` 在停机时直接清零：`BALANCE/system.c:164-215`

`Balance_task()` 再在 100Hz 周期内直接读取 `Move_X/Move_Y/Move_Z` 做逆解和 PWM 输出：`BALANCE/balance.c:241-276`

这意味着当前系统不是“runtime/主环仲裁后执行”，而是“多个路径先改最终命令，主环被动消费”。

## 2. 当前问题

### 2.1 多上下文共同写最终控制量

风险：

- 模式切换时命令状态不一致
- RC 与串口相互抢写
- fault/stop 时只能靠末端清零兜底

### 2.2 启动状态来源不统一

当前存在两套启动计时：

- `Time_count`：`Balance_task` 中递增，`BALANCE/balance.c:249-258`
- `Deviation_Count`：`MPU6050_task` 中递增，`HARDWARE/MPU6050.c:42-52`

同时：

- `UART4_IRQHandler()` 用 `Time_count` 判断是否允许接收控制：`HARDWARE/usartx.c:491-500`
- `tr800_runtime_update()` 用 `Deviation_Count` 判断 boot delay：`BALANCE/system.c:146-181`

这会造成“串口路径”和“runtime 路径”对系统启动状态理解不一致。

### 2.3 runtime 目前不是唯一仲裁中心

`TR800_Runtime` 目前管理了：

- `system_state`
- `requested_mode`
- `active_mode`
- `serial_last_rx_ms`
- `rc_last_rx_ms`
- `fault_flags`

但它并没有真正拥有“当前生效运动命令”的所有权。  
当前它更像“状态记录器 + 停机清零器”。

## 3. 第一阶段目标链路

第一阶段目标链路如下：

```text
UART4 ISR / USART2 ISR
  -> 原始接收缓冲 / 通道缓存
  -> SERIAL 命令快照 / RC 命令快照
  -> Balance_task
  -> active command
  -> Drive_Motor()
  -> PI
  -> PWM
```

约束只有一句：

> 只有 `Balance_task` 可以把输入快照变成当前生效运动命令，并进一步生成电机目标和 PWM。

## 4. 推荐分层

### 4.1 ISR 层

职责：

- 收字节
- 成帧
- 更新时间戳
- 标记“有新帧/有新数据”

禁止事项：

- 禁止写 `Move_X/Move_Y/Move_Z`
- 禁止请求 `TR800_MODE_SERIAL/RC`
- 禁止直接决定 PWM

### 4.2 输入快照层

建议至少保留两个命令快照：

```c
typedef struct
{
    float x;
    float y;
    float z;
    uint32_t rx_ms;
    uint16_t seq;
    uint8_t valid;
} TR800_CmdSnapshot;
```

建议实例：

- `g_serial_cmd`
- `g_rc_cmd`

职责：

- 串口路径只更新 `g_serial_cmd`
- 遥控路径只更新 `g_rc_cmd`

### 4.3 runtime 层

`TR800_Runtime` 只负责：

- boot delay
- enable/fault
- alive 状态
- 当前模式状态

不再直接清理共享控制总线，不再顺手改最终命令。

### 4.4 主控制层

`Balance_task` 每个 10ms 周期负责：

1. 读取编码器
2. 更新 runtime
3. 读取 `g_serial_cmd`
4. 读取 `g_rc_cmd`
5. 完成模式仲裁
6. 生成本周期 `active_cmd`
7. `Drive_Motor(active_cmd.x, active_cmd.y, active_cmd.z)`
8. PI 和 PWM 输出

## 5. 模式仲裁规则

建议第一阶段只保留以下仲裁顺序：

1. 若 `boot delay / enable / low voltage / stop fault` 不满足，输出零命令
2. 若 RC 模式选择有效且 `g_rc_cmd.valid=1`，使用 `RC`
3. 否则若 `g_serial_cmd.valid=1`，使用 `SERIAL`
4. 否则输出零命令

也就是：

```text
system state
  -> source validity
  -> active mode
  -> active command
```

而不是：

```text
ISR / RC task
  -> requested_mode
  -> 直接改 Move_XYZ
```

## 6. 各任务在主链路中的位置

### `Balance_task`

- 周期：100Hz
- 地位：唯一运动输出主环
- 必须高于 `RC_task` 和 `data_task`

### `RC_task`

- 周期：IBUS 50Hz / SBUS 80Hz
- 地位：输入生产者
- 只产出 `g_rc_cmd`

### `data_task` / `comm_task`

- 周期：40-50Hz
- 地位：通信任务
- 第一阶段建议同时负责：
  - 消费 UART4 新帧
  - 解析并更新 `g_serial_cmd`
  - 遥测发送

### `MPU6050_task`

- 周期：100Hz
- 地位：采样任务
- 不再承担 boot delay 主时间基

### `show_task`

- 周期：10Hz
- OLED 实刷：2Hz
- 地位：只读诊断显示

### `led_task`

- 地位：状态提示
- 不得再写其他控制状态

## 7. 停机与失联规则

第一阶段建议统一如下：

- `SERIAL` 超时：`g_serial_cmd.valid=0`
- `RC` 超时：`g_rc_cmd.valid=0`
- `fault / enable off / low voltage / stop request`：`Balance_task` 输出零命令

不要再让多个模块分别：

- 改 `requested_mode`
- 清 `Move_X/Y/Z`
- 各自做一套“停机判断”

## 8. 迁移顺序

建议顺序：

1. 缩小 `UART4_IRQHandler()`
2. 收缩 `rc_loop_control()`，改为只生成 RC 命令快照
3. 新增 `g_serial_cmd` / `g_rc_cmd`
4. 在 `Balance_task` 内实现统一仲裁
5. 移除 `runtime` 对 `Move_X/Y/Z` 的直接清零
6. 统一 boot delay 时间基

## 9. 第一阶段完成标准

满足以下条件，说明控制链路已经从“抢写式”转为“主环仲裁式”：

- 没有 ISR 直接写 `Move_X/Y/Z`
- 没有 RC 路径直接写 `Move_X/Y/Z`
- `TR800_Runtime` 不再直接操作共享控制总线
- `Balance_task` 是唯一把输入命令变成电机目标和 PWM 的任务
- `SERIAL/RC` 切换时不会复用旧命令
