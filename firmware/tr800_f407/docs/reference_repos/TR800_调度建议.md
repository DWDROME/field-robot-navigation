# TR800 调度建议

本文档基于当前 TR800 代码现状给出更具体的调度建议，不以“重做框架”为目标，而以“先把运动状态主线收口”为目标。

## 1. 现状

当前任务创建：`USER/main.c:21-33`

当前优先级定义：

- `RC_task = 5`：`HARDWARE/usartx.h:10-13`
- `Balance_task = 4`：`BALANCE/balance.h:5-8`
- `data_task = 4`：`HARDWARE/usartx.h:7-9`
- `show_task = 3`：`BALANCE/show.h:5-7`
- `led_task = 3`：`HARDWARE/LED.h:6-8`

当前周期：

- `Balance_task` 100Hz：`BALANCE/balance.c:249-256`
- `RC_task` IBUS 50Hz / SBUS 80Hz：`HARDWARE/usartx.c:1548-1552`
- `show_task` 10Hz，OLED 实刷约 2Hz：`BALANCE/show.c:20-25`, `BALANCE/show.c:79-85`

当前核心问题：

1. `UART4_IRQHandler()` 直接写 `Move_X/Y/Z` 和模式。
2. `RC_task()` 直接请求模式并通过 `rc_loop_control()` 写 `Move_X/Y/Z`。
3. `Balance_task()` 读取的是一个被多个上下文共享写入的最终控制量。

这会让调度问题变成状态所有权问题，而不仅仅是优先级问题。

## 2. 最小可落地改法

不新增复杂框架，只做以下收口：

### 2.1 保留全局，但按语义分层

建议新增两个全局快照：

```c
typedef struct
{
    float x;
    float y;
    float z;
    uint32_t rx_ms;
    uint16_t seq;
    uint8_t valid;
} TR800_SerialCmdSnapshot;

typedef struct
{
    float x;
    float y;
    float z;
    uint32_t rx_ms;
    uint16_t seq;
    uint8_t valid;
} TR800_RcCmdSnapshot;
```

写者约束：

- `UART4` 接收路径只更新 `g_serial_cmd`
- `RC_task` 只更新 `g_rc_cmd`
- `tr800_runtime_update()` 只更新运行状态和 fault
- 只有 `Balance_task` 可以把这些快照仲裁成当前生效命令

## 3. 推荐任务职责

### A. `Balance_task`

优先级：最高  
建议优先级：`5`

周期：100Hz，不改

职责只保留：

1. 编码器采样
2. `tr800_runtime_update()`
3. 读取 `g_serial_cmd` / `g_rc_cmd`
4. 决定 `active_mode`
5. 生成本周期 `active_cmd`
6. `Drive_Motor(active_cmd.x, active_cmd.y, active_cmd.z)`
7. PI 与 PWM 输出

不再允许：

- 读取未经仲裁的原始串口命令
- 依赖 ISR 直接写入的 `Move_X/Y/Z`

### B. `RC_task`

建议优先级：`4`

周期：

- IBUS 保持 50Hz
- SBUS 保持 80Hz

职责只保留：

1. `RC_Read()`
2. 通道归一化
3. 生成 `g_rc_cmd`
4. 更新 RC alive 时间戳

不再允许：

- `tr800_runtime_request_mode(TR800_MODE_RC)`
- 直接写 `Move_X/Y/Z`
- 直接抢占 SERIAL 生效命令

### C. `comm_task`（建议由现有 `data_task` 演进）

建议优先级：`3`

建议周期：50Hz

职责：

1. 消费 `UART4_IRQHandler()` 缓存的完整帧
2. 校验并解析为 `g_serial_cmd`
3. 更新 serial alive
4. 周期发送遥测

建议不要再让 `data_task` 只是“发数据”，否则串口接收与串口状态仍然分裂。

### D. `show_task`

建议优先级：`2`

周期保持 10Hz 也可以，但：

- OLED 刷新频率维持 2Hz
- 电池采样次数下调
- 只读诊断快照

### E. `led_task`

建议优先级：`1`

只负责状态灯，不参与控制。

## 4. 推荐优先级表

| 任务 | 当前 | 建议 | 原因 |
|---|---:|---:|---|
| `Balance_task` | 4 | 5 | 主控制环必须是唯一运动输出者 |
| `RC_task` | 5 | 4 | RC 是输入生产者，不该压过运动主环 |
| `comm_task/data_task` | 4 | 3 | 串口解析和遥测不应抢占主控制 |
| `MPU6050_task` | 3 | 3 或 4 | 若采样确实敏感可保持较高，否则与通信同级 |
| `show_task` | 3 | 2 | 显示必须低优先级 |
| `led_task` | 3 | 1 | 状态提示最低即可 |

## 5. 推荐时序

### 每个 10ms 控制周期

```text
Balance_task
  -> 读取编码器
  -> runtime_update(now)
  -> 读取 g_serial_cmd / g_rc_cmd
  -> mode arbitration
  -> active_cmd
  -> Drive_Motor()
  -> PI
  -> Set_Pwm()
```

### 串口输入路径

```text
UART4_IRQHandler
  -> 收字节
  -> 完整帧就写 rx_buffer + frame_ready_seq
  -> 退出

comm_task (50Hz)
  -> 发现新 frame_ready_seq
  -> 校验
  -> 更新 g_serial_cmd
```

### 遥控输入路径

```text
USART2 IRQ / DMA callback
  -> 收原始数据
  -> 更新时间戳

RC_task
  -> RC_Read()
  -> 归一化
  -> 更新 g_rc_cmd
```

## 6. 模式仲裁建议

建议不要再让 `RC_task` 和 UART ISR 各自请求模式。

更稳的规则：

1. `Balance_task` 内先判断 `runtime state`
2. 若 `fault / disable / stop`，直接输出零命令
3. 若 RC 选择开关有效且 `g_rc_cmd.valid=1`，使用 RC
4. 否则若 `g_serial_cmd.valid=1`，使用 SERIAL
5. 否则输出零命令

也就是：

```text
system state
  -> source availability
  -> active command
  -> motor target
```

而不是：

```text
ISR / RC task
  -> 直接抢 Move_X/Y/Z
```

## 7. 为什么不建议现在引入消息队列

事实：

- 你们当前系统规模还不大。
- 真问题是“多人写同一个控制量”，不是“没有中间件”。

推断：

- 用全局快照 + 单一写者，已经足够解决当前主线问题。
- 现在引入队列、事件总线、复杂模块层，只会增加调试成本。

## 8. 实施顺序

1. 先收缩 `UART4_IRQHandler()`
2. 再让 `RC_task()` 改成只产生命令快照
3. 最后在 `Balance_task()` 内完成统一仲裁

这个顺序的原因很简单：先堵住 ISR 抢写，再堵住 RC 抢写，最后把唯一生效入口定在主环。
