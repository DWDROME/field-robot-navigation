# FAST-LIO Super 后续演进深度调研报告

## 主线校准

按你给出的 briefing 来看，你们已经做对了最重要的一步：把前端里的地图结构从“写死的 ikd-tree”抽成接口，并把 Super-LIO 的紧凑地图管理作为 active map 的可插拔选项。这条线没有走偏，因为公开资料里 entity["organization","HKU MaRS Lab","robotics lab"] 的 FAST-LIO2 本来就是一个“高性能前端”：核心是 IESKF、原始点直接 scan-to-map、以及 ikd-tree 维护的局部地图；而 Super-LIO 的公开论文与仓库说明强调的是 compact mapping、HKNN、relocalization 与多传感器适配，而不是一套已经完成的 keyframe–pose graph–long-term map 产品。换句话说，把 Super-LIO 的地图管理吸收到 FAST-LIO2 里，是在强化前端能力，不是在替代后端。citeturn16search0turn18view0turn16search1turn18view1

真正容易“走偏”的地方，不是你们目前已经完成的接口化，而是如果后续继续把大量时间投入在 OctVox 热路径微优化，并期待它同时承担 active registration map、长期真值地图、以及规划地图三种角色。过去两年更现代、也更有体系感的系统——包括 MOLA、KISS-SLAM、GLIM、PIN-SLAM——都在强化“地图分层”而不是“唯一地图结构”：MOLA 明确把 simple-map 作为视图级真源，并支持 localization-only；KISS-SLAM 组合的是 KISS-ICP、MapClosures 与 g2o，而不是让一个近邻查询结构变成全部；GLIM 则把 mapping 主流程、约束注入、手工校正和多会话合并分开；PIN-SLAM 更进一步，用可变形的隐式地图解决全局一致性，但同样不是把局部 scan-to-map 结构直接当成唯一真源。这个趋势和你们提出的“三图分离”判断是一致的。citeturn18view5turn23view0turn23view1turn18view6turn24view0turn34view0turn34view1turn18view8turn18view7

因此，接下来最该补的不是更多前端小修，而是系统骨架：**keyframe store、pose graph backend、loop candidate provider**。这是过去几年 FAST-LIO 社区魔改、MOLA 的 simple-map 思路、KISS-SLAM 的轻量后端化路径，以及 LiLoc 这类长期定位框架共同指向的结论。我的判断是：你们的主线没有偏，但工程注意力该从“active map 做得更极致”转为“让 active map 退回前端角色，让系统层长出来”。citeturn19view0turn19view1turn19view4turn32view2turn18view5turn23view2

## 候选系统版图

如果把候选面扩大，最有价值的一类并不是传统意义上的“完整 SLAM 大包”，而是 **FAST-LIO 社区 sidecar 魔改族群**。这类项目的共同结构是：保留 FAST-LIO2 前端，把关键帧、回环、位姿图优化和重定位挂成异步线程或旁路节点。FAST_LIO_SLAM 明确把 FAST-LIO2 与 SC-PGO 分开运行；FAST-LIO-SAM 明确把 PGO 写成相对模块化的结构，并公开了 corrected frame 发布、关键帧检测、iSAM2 优化和 loop 线程；FAST_LIO_LC 更进一步，直接把优化后的结果回写 FAST-LIO 的前端位姿和地图；FASTLIO2_ROS2 则把这整件事推进到 ROS 2，同时加了回环、重定位、以及 BLAM/HBA 一致性地图优化；better_fastlio2 则把动态去除、多会话、LiLoc 重定位等功能打成一个更大包。换言之，**社区共识不是“重写前端”，而是“外挂后端”**，这和你们现在的接口分层非常一致。citeturn19view0turn19view1turn19view4turn19view6turn19view5

但这类项目的“可借鉴价值”并不相同。FAST_LIO_SLAM 的优点是结构最干净：FAST-LIO2 与 SC-PGO 解耦，明确靠 odometry 与点云 topic 交互，因此很适合借它的“sidecar 边界”；但它的 issue 页面在公开抓取中仍以 2022–2023 年的问题为主，说明活跃度与维护节奏已经偏慢，而且仓库抓取结果没有给出清晰的顶层许可证信号，合规上至少要先按“未知”处理。FAST-LIO-SAM 的优点是它把 keyframe queue、loop thread、iSAM2 主循环、corrected frame 这些你们最需要的后端通路写得很清楚，还直接给了 Livox 启动项；缺点是作者明确把该仓库和 QN 版本置于 CC-BY-NC-SA 4.0 之下，这意味着它更适合当“图纸”和“设计参考”，不适合当将来可能商业化产品的代码来源。FAST-LIO-SAM-QN 则证明了 Quatro + Nano-GICP 这类更强验证器是可行的，但其 README 同时也公开了更高 CPU 占用，意味着它是“精度与鲁棒性换算力”的路线，而不是默认答案。citeturn19view0turn20search4turn21search9turn19view1turn19view2turn19view3

FAST_LIO_LC 值得特别重视，不是因为它本身一定最优，而是因为它解决了一个你们迟早会遇到的关键工程问题：**回环后如何影响前端**。它的 README 明确指出，和 FAST_LIO_SLAM 的差异在于它会根据优化结果更新 FAST-LIO 的 ESKF pose 和 map。这说明社区里确实有“回写前端”的一支实践，而不只是外层挂一个 corrected map。不过，它公开 issue 里也出现了 outdoor Z 轴漂移和 double free 等问题，说明“把后端直接写回前端”虽然更彻底，但风险也明显更高；此外它的 loop detection 仍偏朴素，核心是 radius-search。我的判断是：FAST_LIO_LC 很适合借 **map correction / correction bridge 的工程经验**，不适合作为主线后端图纸的唯一来源。它被 entity["organization","Autoware Foundation","autonomous driving org"] 文档纳入开源建图清单，说明至少在工程社区里有现实使用者。citeturn19view4turn20search13turn21search10turn30search6turn20search5

把视野再扩大，真正值得你们认真看的其实是五条更现代的“系统化参考线”。第一条仍然是 LIO-SAM，它最强的不是“它是经典”，而是 **两张因子图分工**——一张长期地图优化图、一张为实时估计周期性重置的 IMU 预积分图——这正好回答你们“前端继续跑、后端异步优化”的系统边界问题。第二条是 MOLA/MOLA-LIO，它最打动人的不是某个单点算法，而是 simple-map、地图操作、以及 localization-only 模式，这对于你们未来做多会话、prior-map localization 和规划地图 sidecar 极其重要。第三条是 KISS-SLAM：MIT 许可、KISS-ICP + MapClosures + g2o、2025 年还有 release，说明“一个轻量、现代、非 GTSAM 霸权的后端”已经存在。第四条是 plain_slam_ros2：核心逻辑不到 1900 行，回环、PGO、localization 都有，而且核心不依赖 ROS 2，只依赖 Sophus、nanoflann 和 YAML，它是非常好的“最小系统骨架”参考。第五条是 GLIM：MIT、335 commits、2026 年仍在发版，显式支持 Livox MID360，提供 global callback slot 让你们把外部约束塞进因子图，还公开了多会话合并和手工校正——它不是最短接入路径，但非常像“未来你们想变成的系统形态”。citeturn18view2turn18view5turn23view0turn23view1turn18view6turn24view0turn34view3turn23view2turn34view0turn34view1

还有一批被很多“FAST-LIO 后端三选一”报告忽略了的新路线，它们未必直接给你后端，但会实质改变你们未来的系统图。SuperOdom/SuperLoc 这条线重视 alignment risk prediction 和 localization mode，把“会不会配准失败”变成一等公民；RKO-LIO 则把“跨 LiDAR 免调参、ROS1/ROS2 包都能吃”的可部署性拉到了很高水位；R-VoxelMap、Hybrid-VoxelMap、CT-VoxelMap、GenZ-LIO、Surfel-LIO 则分别在 2024–2026 年把 plane fitting、混合 voxel、连续时间与自适应 voxel 尺度这些前端和地图层细节向前推了一大步；而 PIN-SLAM、SHINE-Mapping 则代表“跳出经典 keyframe PGO”的隐式地图路线。这些都不是你们 3 个月主线该直接拥抱的核心，但如果你们想“向更好的算法靠拢”，它们是必须纳入观察列表的新前沿。citeturn33view0turn32view3turn32view5turn23view3turn23view6turn28search1turn29search3turn29search19turn17search0turn17search9turn18view8turn18view7

## Mid360 与回环检测

围绕 entity["company","Livox","lidar manufacturer"] Mid-360，你最该关心的不是“哪篇论文名字更响”，而是**公开证据里哪些方法真的考虑了窄垂直 FoV、非重复扫描和稀疏观测**。从驱动层开始，livox_ros_driver2 官方 README 目前仍然同时支持 ROS1 noetic 和 ROS2 foxy/humble/jazzy，但它自己也明确把仓库定位成 debugging tool，而不是 mass production 的成品；2026 年 3 月甚至还有 Mid360s 初始化成功但无 topic 的新 issue。换到回环侧，LIO-SAM 在 2025 年公开 issue 里已经多次出现 Mid360 无法正常跑通或保存建图失败的问题，同时社区又出现了 LIO-SAM-MID360、FAST_LIO_LC 的 Mid360 参数适配分支，以及“Mid360 + FAST-LIO2 上下楼”与“Mid360 + LIO-SAM 建图翻车”并存的 Bilibili 视频。这些信号合在一起的结论很清楚：**Mid360 生态是活跃的，但稳定性远没有形成统一范式**。citeturn18view9turn14search12turn15search2turn15search6turn15search18turn15search14turn21search14turn15search13turn15search9turn15search17

这也意味着一个重要的“未知”：我在这次公开资料调研里，没有找到**专门针对 Mid360 的 scan-to-scan GICP 回环成功率论文级统计**。因此，“Mid360 下单帧 GICP 回环成功率是多少”这件事，今天不能被文献诚实地回答。能明确说的，是公开社区证据更像是在反复提醒你：对 Mid360 这种非重复扫描、垂直 FoV 更受限的传感器，**默认把回环验证建立在 accumulated submap 或 descriptor-first + geometry-second 的两阶段流程上**，会比“拿当前单帧去直接做 GICP 回环”更稳。这是由否定性证据和方法趋势共同支持的推断，而不是已经被 Mid360 专项 benchmark 量化证实的事实。citeturn15search2turn15search6turn15search18turn27search3turn24view1

在回环候选生成这一层，2024–2026 的扩大候选池非常值得你们认真吸收。SOLiD 几乎是为你们这类问题量身定做：它的论文与仓库公开强调“FOV-constrained LiDAR place recognition”，并且直接把 Livox 作为典型场景举例；它的卖点是轻量、快速、显式考虑窄 FoV。ISC 则是更老但仍有效的几何+强度混合 handcrafted 路线。STD 是目前最成熟的 CPU-only handcrafted descriptor 之一，而 BTC 则把全局三角形和局部二值描述子叠加，但截至这次调研，BTC 官方 repo 只有 4 次提交，README 还写着“paper will be available on arxiv soon”，工程成熟度明显弱于 STD。BEVPlace++ 则代表另一端：它不是 Mid360 专项，但论文给出了很硬的 runtime 数字，在 RTX 3090 + i5-7500 上，place recognition 超过 40 Hz，完整 global localization 约 20 Hz，模型只有 17 MB；这说明“轻量 learned descriptor”已经不是不可部署的代名词了，但论文没有给出你们关心的“纯 CPU-only Mid360 实机”答案。LoGG3D-Net 依然强，但公开 repo 更像研究代码，且这次调研没有找到令人放心的 CPU-only 部署证据。citeturn24view1turn24view8turn24view7turn24view6turn25view0turn25view1turn24view2

一旦把场景从温室扩展到南方林地/丘陵，ScanContext-only 的风险就会变成架构问题，而不只是参数问题。2024 年的 dense forest LiDAR place recognition 评测表明，在他们评估的四类方法里，最佳-performing approach 是 Logg3DNet，而且当它被包进更严格的验证流水线后，森林场景能做到约 80% 正确 loop candidate（5 米基线）和 60%（10 米基线）。2025 年的 ForestLPR 进一步把多高度 BEV density 图引入森林 place recognition，报告在 intra-sequence loop closure detection 和 inter-sequence re-localization 上，Recall@1 相比最近基线平均提升 7.38% 和 9.11%。2025 年的 HOTFormerLoc 则把 octree transformer 拉到 urban + forest + cross-view 的统一 benchmark 上，报告 top-1 平均 recall 提升 5.5%–11.5%。2026 年的 TreeLoc 与 TreeLoc++ 更激进：它们直接从“点云 place recognition”切到“森林清查地图/树木几何数据库 place recognition”，TreeLoc++ 甚至报告用 250 KB 的 DFI 地图表示 15 个 session、7.98 km 轨迹，并能在两年间隔的数据上做厘米级定位。这组证据足够支持你们 briefing 里的判断：**ILoopCandidateProvider 一定要插件化**，而且 forest provider 和 greenhouse provider 大概率不是同一个算法。citeturn25view6turn25view7turn25view4turn27search2turn27search12turn27search7turn27search0

如果把这些证据压缩成工程判断，我会这样分层。**事实**：当前最适合作为 Mid360/CPU 基线的是 SOLiD 或 STD，而不是 ScanContext-only；对森林场景，学习式方法已经明显胜过传统单描述子。**推断**：你们的默认 loop pipeline 应该是“局部子图/关键帧库 + 可插拔候选提供器 + 几何验证器”，而不是“单帧 + 固定 GICP”。**未知**：哪一个 provider 在你们自己的 Mid360 bag、南方丘陵和温室数据上最优，这一步必须靠实测，而文献与社区 issue 还不够。citeturn24view1turn24view7turn25view6turn25view4turn27search0

## 长期地图与地图产品

长期地图与 localization-only 这一层，公开开源里目前最值得你们研究的不是“哪个包名最热”，而是**谁已经把 session / submap / prior knowledge 作为一等对象**。LiLoc 是这里最醒目的候选：MIT 许可、graph-based lifelong localization、adaptive submap joining、egocentric factor graph，而且作者 README 明确把它定位为 long-term localization framework。它的含义不是“拿来即用”，而是证明了你们 briefing 里的“长期地图不应等同于 active map”是对的：先验知识应该被组织成可更新、可选择、可拼接的 submap，而不是一坨永远增长的点云。相对地，FAST_LIO_LOCALIZATION 是一条更朴素、更早期的 prior-map localization 路线：它把低频全局定位和高频 FAST-LIO 前端融合，能在预建图上做 0.5–0.2 Hz 级的 global localization，但它仍依赖 Python 2.7、Open3D 0.9，并且作者 TODO 里还明确写着“把全局定位更平滑地融合回 FAST-LIO 状态估计”——这说明它更适合借 localization 桥接思路，不适合当你们长期主干。LTA-OM 则是另一端：它已经把 LIO、loop、optimization、LTA 和 multi-session 放到同一系统里，而且公开页是 Apache-2.0；如果你们后续加强长期地图，这条线很值得看，但它比你们眼下的最小可行后端更重。citeturn32view2turn32view1turn32view0turn18view4

“三图分离”在工程上其实已经有很强的外部支撑。MOLA 的 simple-map 和 metric map 区分得很明确：它能建图、后处理、再进入 localization-only；GLIM 则同时公开了 multi-session merge、manual correction、以及通过 callback slot 注入额外约束的机制；LiLoc 用 adaptive submap joining 管 prior knowledge；PIN-SLAM 则把“全局一致地图”本身变成一个可弹性调整的隐式表示。把这些放在一起看，比较合理的落地方式就是：**active map** 只服务于前端 scan-to-map，允许它是 OctVox 或 ikd-tree；**keyframe store / session store** 保存真正可回放、可重定位、可多会话合并的原始 scan、子图、描述子和位姿关系；**planning map sidecar** 再从 keyframe/session store 派生 occupancy、ESDF、height map 或 traversability。也就是说，你们不应该从 active map 截图来充当唯一历史真值，而应让 active map 只是 keyframe store 的“实时缓存视图”。citeturn18view5turn23view0turn23view1turn34view0turn34view1turn32view2turn18view8

规划地图这一侧，如果你们明确未来要朝 voxel navigation、ESDF 与 traversability 走，CPU-only 候选其实也比过去丰富。Bonxai 是一个很有意思的基础库：MPL-2.0，强调 sparse、unbounded、并在某些场景下比 OctoMap 更快更省内存。Rolling-Bonxai 更贴近机器人系统：它在 ROS 2 里做 rolling local map，并把不用的 chunk 序列化到磁盘，需要时再载入。对于“前端 active map 很小、真值地图很大、规划只关心附近局部体素”的场景，这比把 Super-LIO 的 OctVox 硬改成规划地图更合逻辑。相反，G-VOM 从名字就表明它是 GPU accelerated off-road voxel map，这和你们“主线不接受 CUDA 依赖”的约束相冲突，更适合当技术视野里的参考而不是当前主线。另一个有启发性的公开结果是 2026 的开源 off-road navigation stack：它用 LiDAR 或单目深度得到点云，再派生 height map 与 costmap，在 ROS Noetic 下运行，Jetson Orin 上 LiDAR perception 20 Hz、elevation mapping 16 Hz。这说明“SLAM 真值地图”和“导航消费地图”完全可以异步、异构，而且已经有 off-road 工程文献在这么做。citeturn35view0turn35view1turn35view2turn35view3

温室与林地是否要分成不同参数档，答案几乎肯定是“要”，但比“两套 yaml”更重要的是**场景画像要进入系统抽象层**。温室这种小尺度、结构化环境，适合更密的 keyframe、更小的局部 occupancy 分辨率、以及更激进的 loop 候选频率；林地/丘陵则更适合更大的子图、较弱的几何先验、更保守的回环触发，以及更重的 traversability 和树木/地形抽象。TreeLoc/TreeLoc++ 说明在森林里，地图甚至可以退化成 tree inventory；ForestLPR 与 dense-forest evaluation 则说明森林回环的决定性信息和 urban descriptor 显著不同；off-road stack 的实验又说明 height/traversability 这类地图在非结构化导航里比“纯点云真值”更直接可用。就工程上讲，我更倾向于把这件事做成 `scene_profile` 层，而不是散落在多个 yaml 里。citeturn27search7turn27search0turn25view6turn25view4turn35view3

## 许可证与平台迁移

## 个人综合判断

这是我的**个人综合判断**。如果目标是“让 fast_lio_super 在 3 个月内长成可运维的 SLAM 系统”，我不会再把问题简化成“LIO-SAM、hdl_graph_slam、Voxel-SLAM 三选一”。我会把你们的后续主线定义成一个**拼装式系统工程**：从 FAST-LIO 社区 sidecar 里借 keyframe/PGO 主通路；从 MOLA 借 simple-map / localization-only / map-product 分层思想；从 Mid360/FOV-constrained 与 forest place-recognition 文献里做一个插件化的 `ILoopCandidateProvider`；从 LiLoc 借长期定位与 submap 管理；把 HBA 或 GLIM 级别的一致性地图优化留到第二阶段，而不是第一版就上。这个判断之所以成立，是因为它同时满足了你们的现状约束——ROS1、已有 FAST-LIO2 分支、无 bag、1–2 人、未来要接 voxel navigation——也避免了 CC-NC、GPLv2-only 和“把 active map 当唯一真值地图”这些容易埋雷的路径。citeturn19view0turn19view1turn19view4turn18view5turn32view2turn24view1turn25view4turn27search0turn34view2turn34view0

如果只允许我给出一条最可落地的演进路线，我会选下面这条，但我把它明确标成**个人建议，不是唯一真理**。前端继续保持 FAST-LIO2 + OctVox/ikd-tree 双 backend；立即加一个 **view-based keyframe store**，不要再把 active map 当长期真值；pose graph 先走 iSAM2 sidecar，不要求第一版就有最强 loop，只要求关键帧、相邻因子、回环因子、map-correction bridge 这四件事闭环；loop candidate provider 默认给两个插件，CPU 基线用 SOLiD 或 STD，forest/long-term 插件预留 ForestLPR/TreeLoc/BEVPlace++ 接口；重定位主线优先研究 LiLoc，而不是继续在 FAST_LIO_LOCALIZATION 这类老栈上追加债务；规划地图 sidecar 则从 keyframe store 异步派生 Bonxai/Rolling-Bonxai 一类的 occupancy 或 height/traversability 产品。这样做的好处是，你们既没有被某个 monolith 仓库绑死，也没有把未来通往 ESDF / voxel navigation 的路堵住。citeturn24view1turn24view7turn25view4turn27search0turn32view2turn35view0turn35view1
